# Identity

- **Version:** 1

This specification says who a library and its spaces belong to, and where the library is kept, for one user with several replicas ([6.7](../Design.md#67-spaces-members-and-devices), [6.10](../Design.md#610-users-people-and-devices)). Section 8 adds spaces of one's own besides the personal one, and section 9 their members, roles, invitations, leaving, removing and claims to the admin role ([technical design](../Technical-design.md#13-sharing)). Section 10 covers groups, and section 11 recovery codes. The reasons for the choices are in the technical design's sections on [the engine and nib](../Technical-design.md#16-the-engine-and-nib), [users and people](../Technical-design.md#56-users-and-the-people-in-the-data), [revocation](../Technical-design.md#11-revocation-and-new-keys) and [AI agents](../Technical-design.md#14-ai-agents), and in [apps on one library](../Design.md#611-apps-on-one-library).

A *user* is someone who uses NibKeep; a *person* is someone described in the data. Most people are not users, and a user need not be linked to a person ([users and people](../Design.md#610-users-people-and-devices)). Each space a user belongs to holds an `org.nibkeep.user` entity for them, with their name and their link in that space. Every member can read it, so history can name them. In the personal space, only the user's replicas write it. In a space with members, it is the member's record (section 9). Its link holds when an admin's statement and the user's own agree; each side replaces only its own, as the signing key tells.

A *replica* is one copy of a library, kept by one app or shared by the apps that can reach one container. A *device* is the phone or computer that holds replicas ([apps on one library](../Design.md#611-apps-on-one-library)). Each replica has its own keys and signs its changes, so a change shows which replica made it, and so which app, device and user. People see a replica as the app on the device, such as "nib on laptop". A lost device is revoked with all its replicas.

**Who made a change.** The replica whose verifying key is the change's author ([Log](log.md#1-changes)) made it. If several replicas claim one key, which only a faulty replica does, the one with the smallest ID counts. History names the replica's owner by the person linked to that user in the space, in the reader's best form ([Data model](model.md#11-languages-and-scripts)), or else by the user's own name. A change by an AI agent's replica (section 5) is named by the user and by the replica's name, which is the AI agent's, such as "Ada, through Claude". When a replica's record no longer holds its key or owner, as after a change took them away, the counting governing changes say which replica and user it is. A change signed by a key that no replica of the space has names nobody. In this version, that includes a key its replica no longer has, and the keys of deleted replicas; a revoked replica's record stays (section 4). A deleted linked person names nobody either, and the user's own name is shown.

**Languages.** An app shows values by a ranked list of languages ([Data model](model.md#11-languages-and-scripts)): its replica's if it has one, else its device's, else the user's, else none. So a user who reads English and Russian can have a work phone that shows English only, and an app for learning French that shows French first. The lists are in the user's personal space, so any of the user's replicas can change any of them. A list that cannot be read counts as not set.

**Names.** A user and their linked person usually share a name. A name that finds both finds the person, so people who look for themselves find themselves in the data.

The field `org.nibkeep.name`, of the kind Name, is the name of every entity that has one: a user, a person, a device, a replica, a space, and also a city or a company. It has one value at a time, in as many forms as needed ([Data model](model.md#11-languages-and-scripts)).

## 2. A new library

A replica that starts a library founds the user's personal space. It draws a random space ID and a random space key, number 0, and commits the space's first changes:

1. A governing change ([Log](log.md#1-changes)). On the replica's record, derived from the space and its key as in every space (section 8), it asserts the replica's verifying key, its encryption key, the user as its owner, its listing, which its key signs, and each field that the standard vocabulary makes secret, such as `std.password`, as `org.nibkeep.secret-field` ([Data model](model.md#9-secret-fields)).
2. A change with the definitions of the standard vocabulary's types.
3. A change for each of these entities ([technical design](../Technical-design.md#62-one-entity-per-change)):
   - the user, with the name the user gave, as a Name with only its part `"full"` and no qualifiers, linked to the person, and with the languages the user reads, if the user gave any;
   - the person, with the same name;
   - the device, with its name in the same way;
   - the replica, with the app's name in the same way, on the device;
   - the space's own entity, with the name `Personal` in the same way.

The library file records the IDs of the user, the device, the replica and the personal space ([Storage](storage.md#1-layout)).

## 3. A new replica

A user's replica adds another, on another device or in another app, by pairing with it ([Sync](sync.md#2-pairing)). The new replica makes its own keys and sends its verifying key, its encryption key, and its device's and app's names. Before sending the space keys, the replica that adds it, the *sponsor*, commits a governing change of the personal space, then a change for each entity. The governing change asserts, on the new replica's record, derived from the space and its key (section 8):

- its verifying key, its encryption key, and the user as its owner;
- its listing, which its key signed and pairing brings ([Sync](sync.md#2-pairing));
- each space key it grants, except key 0 and those whose rotation does not count, as `org.nibkeep.space-key` (section 4);
- the secrets keys given, if the new replica asks for the secrets and the person chose to give them (section 6).

The other changes assert:

- the new replica, with the app's name, on its device, and with the endpoint ID it connected from;
- its device, with the device's name, on a record derived from the space and the replica's key. It is a new device each time, as this version cannot yet tell a device that already holds a library from another.

Names are written as in section 2. A replica whose own record lacks its encryption key or endpoint ID, as a library's first replica does at first, asserts them in its own changes before it adds another, and when it starts to sync.

The new replica's library file records the IDs that the grant gives: the user, the new device, the new replica and the personal space. Its spaces are empty until its first sync.

**The list of replicas.** A space's replicas are those whose keys its counting governing changes list (section 4), whatever their records say. A replica whose record is deleted is shown as deleted and no longer listed, but it is still synced with until it is revoked, and its changes still count: keys alone decide who may sync. In this version every replica of the user may add others, as every replica may govern the personal space; who may govern shared spaces comes with members. A revoked replica (section 4) is not synced with, and only those of its changes count that every replica which revoked it had. If a pairing fails, the sponsor revokes the new replica's key, as the new replica got the space keys.

## 4. Revoking replicas

A user's replica revokes another, or all the replicas of a device such as a lost phone, with a governing change of the personal space ([technical design](../Technical-design.md#11-revocation-and-new-keys)). The change asserts `org.nibkeep.revoked` on each revoked replica's record, once for each key of the record but its own, with that key as the value. A revocation is final: a device that turns up again is paired again, as a new replica. The record stays, so history keeps naming what the replica signed. The [log](log.md#8-which-changes-count) says which of its changes still count and which are set aside. A replica never revokes itself.

**Who is who.** The counting governing changes say who the replicas are, never the state, which ordinary changes also write to; retractions are left out. In every space, a key is listed only by its own listing, on the record derived from the space and the key (section 8). So a replica's record lists only its key, its *key of its own*, and no replica lists a key on another's record. A replica's encryption key is the one its listing signed, as the change that lists it states it, and no other. The keys sealed to a replica are those that counting `org.nibkeep.space-key` statements on its record give.

**What a revoked replica added.** In each space with members and each group where it is listed, as it carries a revocation there and after each sync, a user's replica also revokes each replica there that:

- has a latest counting listing that names the member the revoking replica is listed for;
- is not listed by the personal space;
- had its key listed for that member by a replica that the personal space revokes, by a counting change there or in another space or group the revoking replica holds. For a key listed by a recovery code, it is enough that a statement by such a replica names the code there. A replica listed in turn by one that meets this meets it too.

It spares a replica that a replica the personal space lists and does not revoke listed too, or one so listed in turn. It acts only once, for each other replica that the personal space lists and does not revoke, except AI agents', the latest account of that replica in the personal space ([Log](log.md#11-accounts-of-copies)) names heads that the revoking replica holds, whose payloads it applied, and that build on each counting revocation of those keys. By then it knows whatever such a replica listed or heard of. In the personal space, what a revoked replica listed that its revocation does not build on no longer counts anyway ([Log](log.md#8-which-changes-count)); the [technical design](../Technical-design.md#11-revocation-and-new-keys) says why other spaces need this rule.

**A new key.** The revocation gives the space a new key, so the revoked replicas cannot read what is added later. Its number is a random 64-bit number that no key of the space the replica knows of has, among those it holds and those that `org.nibkeep.space-key` statements name, so keys that two replicas make at once differ. The same change asserts `org.nibkeep.space-key` on the record of each replica that remains, the revoking one included. The value is the canonical encoding of `[epoch, key hash, sealed key]` in base64url without padding: the key's number; its hash, computed as a change key's is ([Log](log.md#1-changes)); and the key sealed to the replica's encryption key with the context `nibkeep 2026-10 space keys` and the associated data `[space, epoch, replica]`, as pairing seals it ([Sync](sync.md#2-pairing)). A replica *remains* if its keys are listed and none is revoked, it has an encryption key, and, in a space with members, its member did not leave and was not removed, nor is it an AI agent's where the space now allows no AI agents (section 9). A recovery code that stands is given each key on its own record, as a replica that remains is (section 11). Like every governing change, the change is wrapped with the space key of number 0, which every replica holds, so those it gives keys to can read it ([Log](log.md#8-which-changes-count)).

**Taking keys.** A key's *rotation* is the earliest statement of its number that the replica can read, by timestamp and then by ID, whether its change counts or not; for key 0, it is the space's first change. A key is *given out* if the replica that made its rotation was, by the governing changes the rotation builds on, listed by a counting change and revoked by none, and, in a space with members, a replica of a member whose role there was not `none` ([Log](log.md#8-which-changes-count)). This holds whatever later sets the rotation aside, so a key that a member made while being removed is given out all the same ([technical design](../Technical-design.md#13-sharing)). A change that counts was made so.

A replica takes the keys sealed to it in statements made so, whether their changes count or not. It opens each whose number it lacks, keeps it if it is given out and its hash is the one that both the statement and the rotation name, and saves it with its other keys. Where a counting statement whose rotation counts names a number, only such statements give it. A number that only other statements name is taken only if they all name one hash. The replica holds key 0 already, and it is never given out. A key is known by its number and its hash: a statement of a number with another hash is of another key. A revoked replica that held a key can state it again, dated before its rotation, through a replica that has not heard of the revocation, and a removed member can make up a key. Such keys are given out but never written with, as their rotations know nothing of the departure. The replica then reads the changes and blob keys it could not read before.

**Giving keys.** After each sync, in one governing change, a replica seals each key of the space that it holds and that is given out, except key 0, to every replica that remains, itself included, and to every recovery code that stands (section 11), that has no statement of that key made as above. Pairing states the keys it grants in the same way.

**Writing.** A key is *safe* if each of these is its rotation or an ancestor of it: every counting revocation, of a replica's key or of a recovery code (section 11), and, in a space with members, every counting change that ends replicas there (section 9). A replica writes with the newest key it holds that is given out and safe, the one whose rotation is latest, by timestamp and then by ID. If none is safe after a sync, as after two revocations made at once, after someone left, or on a replica paired while a revocation was on its way, the replica writes with the newest key it holds whose rotation counts, or key 0, never one that someone made as they were removed. It also makes a new key and gives it to the replicas that remain, as a revocation does, in a governing change that revokes nothing.

**Accepting.** A set-aside ordinary change of a revoked replica counts once a counting `org.nibkeep.accepted` statement names it, in a change by another replica that builds on it. NibKeep asserts the statement on the record of the replica that made the change, in a governing change. A governing change is never accepted. In a space with members, only an admin accepts, after review ([Log](log.md#8-which-changes-count)). A program lists each change set aside there with the member whose replica made it, by the listings it builds on; the entities it changes, named as the space names them, or else as the change does; and whether accepting would make it count. It would only if the replica can read it and the member's role, by the changes it builds on, allowed it. The program accepts only those.

A replica that sees itself revoked changes nothing, but still syncs, as a revocation it has not heard of may set its own revocation aside.

An AI agent's replica (section 5) is revoked alone, like any other, by its name or ID. Pairing gave it a device record of its own, so revoking it leaves the user's other replicas on the same computer as they were. An AI agent's key that a replica keeps is revoked the same way. Its record is on that replica's device, so revoking the device revokes it too. Pairing names AI agents' device records after the computer they run on, so a device's name names none of their replicas and is not taken for two devices.

A revoked replica that held the secrets keys can still read the secret values it had, but none added later: their changes are sealed with the space's new key, and their values with a new secrets key once a replica that holds the secrets has them unlocked (section 6). As every replica governs the personal space, a revoked replica could have listed replicas of its own while it was trusted, which stay until they are revoked too.

## 5. AI agents

An AI agent acts as a replica of its user, with keys of its own ([technical design](../Technical-design.md#14-ai-agents)). A user's replica adds it by pairing (section 3), with two differences: the replica is named after the AI agent, and the governing change that lists its key also asserts `org.nibkeep.ai-agent`, `true`, on its record. It never gets the secrets keys (section 6).

**Whose key is an AI agent's.** A key is an AI agent's if the governing change that first lists it, in the order of the [log](log.md#8-which-changes-count), asserts `org.nibkeep.ai-agent` on the record it lists the key for. A later statement of that field, or a later listing of the same key, changes nothing: a replica added as an AI agent's stays one, and a user's replica never becomes one.

**What its changes may do.** An AI agent's change counts only if it governs, purges and seals nothing, and asserts only statements that an AI agent may write; the [log](log.md#8-which-changes-count) sets the others aside. An AI agent may assert:

- every field whose name does not start with `org.nibkeep.`;
- `org.nibkeep.name`, `org.nibkeep.deleted`, `org.nibkeep.merged-into`, and the fields of ordered lists, `org.nibkeep.list`, `org.nibkeep.item` and `org.nibkeep.position` ([Log](log.md#4-ordered-lists));
- `org.nibkeep.type`, of every type whose name does not start with `org.nibkeep.`, and of `org.nibkeep.membership`.

It asserts no statement with the qualifiers of a move's note, `org.nibkeep.carried-from`, `-by`, `-at` and `-replaced`, which only a move writes ([Data model](model.md#4-qualifiers)), nor with a migration's, `org.nibkeep.migrated-from` ([Data model](model.md#12-migrations)). So it sets nothing of the library's own records: users, devices, replicas, spaces, type definitions, and storage policies and rules. It may still delete, restore, rename or merge any entity, and take statements away. Its own replica does none of these to the library's own records or to a Git repository's record, nor takes away a statement of a field of NibKeep's own that it may not assert, though every replica would take such a change ([technical design](../Technical-design.md#14-ai-agents)). A field once secret stays secret all the same ([Data model](model.md#9-secret-fields)), and a replica whose endpoint was taken away states it again at its next sync.

**Its spaces.** An AI agent's replica holds the personal space and the other spaces that the person chooses when pairing it, and no others ([technical design](../Technical-design.md#13-sharing)); changing them takes a new pairing. The grant names each chosen space with the user's member record there ([Sync](sync.md#2-pairing)). The AI agent's key signs its listing in each, as an AI agent's, and sends the listings as it says that it joined. Before it commits anything, the sponsor checks each listing, as an invitation checks a joiner's (section 9). It then lists the AI agent's replica in each space, owned by the user's member, with `org.nibkeep.ai-agent` on its record and its app named after the AI agent, and gives it the space's keys. It gives it each space through the personal space, with an entry (section 8), committed with its records in the personal space. The AI agent's replica takes the spaces that the entries on its record give it, and asks for, lists and gives nothing. The user's other replicas give it no space. In a space with members, its listing counts only where the space's admins allow AI agents ([Log](log.md#8-which-changes-count)). Before it shows the code, the sponsor checks that each chosen space allows them, or that its member is an admin there, who then allows them once the AI agent's replica has joined, before listing it. Every member sees which replicas of the space are AI agents'.

**An AI agent's key kept by a replica.** A user's replica can keep an AI agent's key for an AI client on its own device ([technical design](../Technical-design.md#14-ai-agents)). It makes the key, which signs its own listing in the personal space as an AI agent's. The replica lists the key in a governing change of its own, on the record derived from the personal space and the key, with its encryption key, its owner, `org.nibkeep.ai-agent` and that listing. The record is named after the client, is on the replica's device, and has no endpoint. Every replica counts the key's changes as an AI agent's replica's; nothing else tells them apart. The replica keeps the key's private half in its folder, sealed with its storage key ([Storage](storage.md)).

An AI agent's replica makes no change that it knows would be set aside: it gives no keys, makes no new key, and records no endpoint of its own, which the replica that paired it recorded. Admins who stop allowing AI agents in a space end their replicas there, as a removal does (section 9). What an AI agent writes there counts only where the space allows AI agents at the change; what it wrote without knowing that they stopped is set aside. No replica gives it keys there any more, the others give the space a new key, and a sync sends it only what the space held when they stopped. Allowing AI agents again brings back those listed before.

## 6. Secrets

The values of secret fields are sealed with the space's *secrets key*, which only the replicas that the person chooses hold ([6.9](../Design.md#69-secrets), the [technical design](../Technical-design.md#12-secrets)). A replica keeps its secrets keys in its key file's secrets compartment, apart from its other keys ([Keys](keys.md)).

**A key to receive with.** Besides its secrets keys, a replica's secrets compartment holds an X-Wing seed of its own, the *secrets decryption key*. Its public half, the *secrets encryption key*, is stated on the replica's record as `org.nibkeep.secrets-encryption-key`, in the text form of `org.nibkeep.encryption-key`, and the replica it takes the secrets from as `org.nibkeep.secrets-from`. Both are stated in governing changes signed by the replica's key of its own (section 4): not in the change that lists it, nor with another key listed on its record. A replica with no key of its own says nothing that counts of the secrets: it is given none and takes none. Of the counting statements, the latest in the order of the [log](log.md#8-which-changes-count) counts. A key sealed to it opens only inside the secrets compartment, so the library's passphrase never opens the secrets.

**Asking.** A replica that holds no secrets keys, while another does, asks one that holds them and is not revoked, as the person chooses. It states its secrets encryption key in each space where its key is its own, and the replica it asks in the personal space. Then it makes its secrets compartment, with its secrets decryption key and no secrets keys yet, protected by a passphrase or keystore entry of its own and never by the replica compartment's passphrase. A replica that asked may ask another instead, by stating that one.

**Giving.** The replica asked gives the secrets keys of a space when the person chooses to, with the secrets unlocked. In a governing change, it states `org.nibkeep.secrets-key` on the asking replica's record for each secrets key not given to it yet. The value is the canonical encoding of `[epoch, key hash, sealed key, recipient, link]` in base64url without padding:

- the key's number;
- its hash, computed as a change key's is ([Log](log.md#1-changes));
- the key sealed to the asking replica's secrets encryption key with the context `nibkeep 2026-10 secrets keys` and the associated data `[space, epoch, replica]`;
- the BLAKE3 hash, written as a hash, of that encryption key's 1,216 bytes;
- a *link*, which proves that the giver holds a secrets key ([technical design](../Technical-design.md#13-sharing)).

A link is `[space, epoch, tag]`: the space and number of a secrets key that the giver holds, and BLAKE3 in keyed mode, with the key derived from that secrets key with the context `nibkeep 2026-11 secrets links`, of the canonical encoding of the statement's `[space, epoch, key hash, replica, recipient]`. Only a replica that holds that secrets key can make the link, and only one that holds it can check it. The replica asked links each key with itself. In the same act, it gives the asking replica, now known to hold the personal space's secrets, the keys of every other space that it would give it after its secrets settle (below), linked with the personal space's key just given. So one gift brings the secrets of every space where the asking replica stated its secrets encryption key. A replica gives none to a replica that asked another, nor to an AI agent's replica (section 5), nor while it has no key of its own.

**Giving to those that hold them.** After its secrets settle, while they are unlocked, a replica with a key of its own that holds secrets keys of a space and remains there (section 4) gives each of them whose rotation a member's replica made, as for space keys (section 4). It gives them, in one governing change, to every replica *known* to hold the secrets that has no statement of that key that this replica can trust. A replica is known to hold them if it remains, is not an AI agent's, has a secrets encryption key, and either:

- this replica gave it a key;
- a counting statement gives it one, to that encryption key, with a link that a key this replica holds checks, of the same space or the personal space; or
- this replica takes the secrets from it.

A statement of a key given to a replica can be trusted if this replica made it, or its link checks so, or the replica that the other takes the secrets from made it. Each gift is linked with the newest key, by its rotation, that this replica holds and the other was given in a statement it trusts, so the other can check the link; or else with the key itself. A replica that says it takes the secrets from itself, and gives itself a key of its own making, is known to hold them by no other, as no key they hold checks its links.

**What is given to a replica.** The secrets keys given to a replica are those that counting `org.nibkeep.secrets-key` statements on its record give it, whose recipient is its secrets encryption key, in changes signed by the key of its own of the replica it takes the secrets from. Every other statement is ignored, except one whose link a secrets key the replica holds checks, of the same space or of the personal space, which only the user's own replicas hold.

**Taking.** A replica takes the secrets keys given to it while its secrets compartment is open: when its secrets are unlocked, and after each sync while they are. It opens each whose number it lacks with its secrets decryption key. It keeps it if its hash is the one stated and either the replica it takes the secrets from gave it, or its link was made with a secrets key it holds, in a statement and for a key whose rotation a member's replica made, as for space keys (section 4), whether their changes count or not. A key it keeps may check the link of another, so it takes keys until none is left to take. It saves the keys it keeps in its secrets compartment, which it reads and writes again while it holds the lock of the key file ([Keys](keys.md)); then it opens the secret values.

**A new secrets key.** A secrets key's *rotation* is the earliest statement of its number and hash that the replica can read, as for space keys (section 4). A secrets key is *safe* if every counting change that revokes a replica that a statement gave a secrets key, or that ends such a replica in a space with members (section 9), is its rotation or an ancestor of it. A replica seals new secret values with the newest safe secrets key it holds whose rotation a member's replica made, by its rotation's time and then by ID; until one is safe, with the newest whose rotation counts.

After its secrets settle, if none is safe, a replica that gives them as above makes a new secrets key. Its number is a random 64-bit number that no secrets key of the space has, among those it holds and those that statements name. The replica saves it in its secrets compartment, and, in one governing change, gives it to itself, linked with the key it sealed with until then, and to every replica known to hold the secrets, linked as above. A revocation made with the secrets unlocked makes one at once. Two replicas that make one at the same time give each other theirs, and both seal with the newer. A replica that held the secrets, and was revoked or removed, can still make one, linked. The others take it, but never seal with it.

Then a compartment is removed if it holds no secrets keys and the counting statements do not give its secrets encryption key as the replica's, with a replica it takes them from, so the replica can ask anew. Such is the compartment of a replica that joined and stopped before it said that it asks, or whose record lists a key that it did not make.

**Adding a device.** A new replica may ask for the secrets as it pairs, with a secrets encryption key in its request ([Sync](sync.md#2-pairing)). If the records say that the sponsor holds the secrets, and they are unlocked there as the person chose, the change that lists the new replica's key gives them, sealed to that secrets encryption key. The sponsor refuses a secrets encryption key that is the new replica's encryption key, which the replica compartment would open. The new replica writes its secrets compartment, with its secrets decryption key and a protection of its own, never the replica compartment's, together with its other keys when it makes its library. After its first sync, if the records say that the sponsor holds the secrets, the new replica states, with its key, its secrets encryption key and that it takes the secrets from the sponsor, whose verifying key the grant named. It takes the keys given, its secrets unlocked, and syncs once more, so the sponsor knows. If the sponsor holds none, it removes the compartment again.

**Who holds the secrets.** A replica sets up the secrets the first time a secret is stored. It makes a secrets key for the personal space, with a random 64-bit number that no secrets key of the space has. It states its own secrets encryption key and that it takes the secrets from itself, and gives the keys to itself. So the records say which replicas hold the secrets: one that takes them from itself, and one given a key by the replica it takes them from, if that replica holds them. Two replicas that say they take them from each other hold nothing. A replica holds the secrets if it has a secrets compartment and either keys are given to it, it states that it takes them from itself, or it states nothing yet. It states nothing yet when setting up its secrets was cut short, and states that it takes them from itself the next time they are unlocked. A replica asked for the secrets if it has a compartment and takes them from another. A replica without a compartment counts another as holding them if a replica that is not revoked does. Where only revoked replicas held them, their secrets are lost, and may be set up anew.

**Another space's secrets.** Each space has secrets keys of its own ([technical design](../Technical-design.md#13-sharing)). Those of a space with members are set up with the first secret value written there, by a replica of an admin of the space whose own secrets are set up and unlocked, if no replica that remains there holds them, as the records give them. It makes a secrets key with a random 64-bit number that no secrets key of the space has, and saves it in its secrets compartment. In one governing change, it states its secrets encryption key; that it takes the space's secrets from itself, which counts only from an admin ([Log](log.md#8-which-changes-count)); and the key given to itself, linked with the personal space's secrets key that it seals with. A replica of another member asks one that holds them, which its person chooses, by stating its secrets encryption key in the space and that replica. The person of the replica asked gives the space's secrets keys, as in the personal space.

A user's replica known to hold the personal space's secrets, as above, is known to hold those of every other space it is listed in where its newest choice of that space in the personal space holds it (section 8). One that never took a space, as a phone listed through a group, or declined it, is given none of its secrets so. Each gift to it that no key of the space links is linked with the newest personal secrets key given to it that the giver holds, and it takes the key with the key of its personal space. A space's secrets need a new key, as above, after the departure of a replica that a statement gave one of its secrets keys, a member's leaving or removal included. The replica that removes a member makes it at once if its secrets are unlocked. Pairing gives only the personal space's secrets; the others follow.

## 7. Copies of a replica

A copy of a replica's folder, which a backup, a program that syncs folders, or a person brought from another computer, drive or folder, is never used as the replica it was ([Storage](storage.md#11-which-replica-is-here), the [technical design](../Technical-design.md#72-copies-of-a-replica)): it signs, adds and revokes nothing. A copy helps this computer become a device of its own, in a new replica beside it:

- **Added by another device.** The new replica pairs as any does (section 3), and takes in what the copy holds and it lacks ([Storage](storage.md#12-what-copies-hold)). If the copy's device is gone, the person revokes it (section 4) from the new device once it has synced, so the revocation builds on all that the copy brought.
- **Added by the copy's own keys,** where no other device can, as after the only device's library was restored from its backup. The copy is opened in a private copy of its own, beside the replicas: its keys in a key file of that copy's, under a newly drawn passphrase, and its spaces empty until they take in what the copy holds, as from another replica. Nothing is written to the copy or its keystore entries. It adds the new replica as pairing does, giving it the spaces that the copy holds except one it drops. Where the copy asks before it takes a space given to it later, it says so for the new replica too (section 8). The new replica takes in what the copy holds, with the copy's secrets if the person unlocks them, then revokes every replica of the copy's device. If any of that fails, the new replica is removed, as no other replica knows it, and the person can begin again. The user's devices that turn up later do not know the new replica, and are added anew.

**The secrets of a copy.** A new replica beside a copy, whose secrets the person unlocks, takes those of the copy's secrets keys that counting `org.nibkeep.secrets-key` statements gave the copy's replica, by number and hash (section 6), and no others. It then holds them as a replica that sets up the secrets does: it states its secrets encryption key and that it takes the secrets from itself, and gives the keys to itself. A replica added by the copy's own keys takes them before the copy's device is revoked, as the secrets of a revoked device alone are lost.

## 8. Spaces of one's own

A user makes spaces besides the personal one, such as *Household*, which hold entities of their own and are later shared as a whole ([technical design](../Technical-design.md#13-sharing)). A user's replica holds the personal space, and each space given to it with the person's consent that it took and has not declined or dropped ([technical design](../Technical-design.md#1310-devices-that-choose-their-spaces)). AI agents' replicas hold the personal space and only the spaces chosen when they were paired (section 5). The personal space is never shared.

**A space with members.** A space other than the personal one has members, each with a record there: an `org.nibkeep.user` entity with the user's ID as `org.nibkeep.user-id`, stated when the record is made, and the member's role as `org.nibkeep.role`. The space's first change gives a role, which tells it from a personal space. A change counts there only if its author's role at it allows it ([Log](log.md#8-which-changes-count)).

**A replica's record and listing.** In every space, the personal one too, a replica's record ID is the first 16 bytes of the BLAKE3 key derived with the context `nibkeep 2026-11 replica records` from the space's ID followed by the replica's verifying key's 32 bytes, as a version 4 UUID. Its device's record there is derived the same way, with the context `nibkeep 2026-11 device records`. So every replica knows whose records they are; only their member's replicas and admins change them. The change that lists the key asserts on that record the key as `org.nibkeep.signing-key`, the replica's encryption key, the member as `org.nibkeep.owner`, and the replica's *listing* as `org.nibkeep.listing`: the canonical encoding of `[space, record, owner, ai-agent, encryption, key, signature]` in base64url without padding, where:

- `ai-agent` is `true` for an AI agent's replica;
- `encryption` is the BLAKE3 hash, written as a hash, of the encryption key's 1,216 bytes;
- `signature` is the key's, with the context `nibkeep listing`, of the canonical encoding of `[space, record, owner, ai-agent, encryption]`.

A listing is the replica's own, as only its key signs it ([technical design](../Technical-design.md#133-members-roles-and-who-is-who)). [The log](log.md#8-which-changes-count) counts no other listing in any space. History names a change's author there by the counting listings alone, never by what the state holds of keys.

**Founding a space.** A user's replica founds a space: it draws a random space ID, a first key, number 0, and the ID of the user's member record, signs its own listing, and commits the space's first changes. The first, which governs the space, asserts the member's user ID and the role `admin`, the replica's listing, and, on the replica's record, each field that the standard vocabulary makes secret, as a new library's first change does (section 2). Then come a change with the definitions of the standard vocabulary's types, and one for each entity:

- the member, of the type `org.nibkeep.user`, with the user's name;
- the replica, with its app's name and its endpoint ID, on its device's record in the space, derived as above, with the device's name;
- the space's own entity, with the name given.

Names are written as in section 2.

**The user's spaces.** The personal space lists the user's other spaces, in governing changes. An `org.nibkeep.space-entry` statement on a replica's record there gives it a space: the canonical encoding of `[space, member, root, key hash, sealed key]` in base64url without padding, where:

- `member` is the user's member record in the space;
- `root` is the ID of the space's first change, written as a hash;
- `key hash` is the hash of the space's first key, computed as a change key's is ([Log](log.md#1-changes));
- `sealed key` is that key sealed to the replica's encryption key with the context `nibkeep 2026-11 first keys` and the associated data `[space, 0, replica]`.

The first key wraps the space's governing changes (section 4), so it cannot come from the space's own log.

**Consent.** A user's replica is given an entry only with the person's consent, by the replica where the person gives it, which seals those it can:

- as they make a space, or join one by an invitation: to every replica of the user's that takes new spaces, as its mark below says, and to those they choose besides;
- as they pair a replica: to it, in the records that pairing commits, for the chosen spaces among those the sponsor holds ([Sync](sync.md#2-pairing));
- as they approve a replica's request on a replica that holds the space (below).

No entry of a space goes to a replica whose newest choice of it in the personal space declined or dropped it, nor to one that has an entry of it already. Nothing records the consent for other replicas to act on.

**New spaces.** A replica says whether it takes the spaces given to it later with `org.nibkeep.new-spaces` on its own record in the personal space, in a governing change: `true` where it takes them, as a computer does, `false` where it asks first, as a phone does. Only statements from a key of that record count, the last by the order of the changes. A replica that states none takes them. A replica paired as a phone states `false` after its first sync, as its grant says ([Sync](sync.md#2-pairing)). A new library made on a phone, on Android or iOS, states `false` as it starts; one made on a computer states none.

**Requests.** A replica asks for a space it was not given, or dropped, by stating a choice to hold it (below) on its own record in the personal space. A user's replica that holds the space, is listed there, holds it by its choices, and whose member did not leave, shows the request of another replica of the user, not revoked and not an AI agent's, whose newest choice of the space in the personal space holds it: as one that came back, where its standing choice in the space is a drop with a lower number; otherwise, where it has no entry of the space and is not listed there. Approving gives it an entry or, for one that came back, states its choice there, as **Choices** below says.

**The names of spaces.** A user's replica keeps in the personal space the names of each space it holds, except the personal one and one whose member left. They are on an `org.nibkeep.space-names` entity whose ID is derived as a replica's record's is, from the personal space's ID followed by the space's ID, with the context `nibkeep 2026-11 space names`. It holds the space's ID as `org.nibkeep.of-space` and the names of the space's own entity as `org.nibkeep.name`. The replica writes them as it makes or joins the space, after a rename, and after each sync where they differ, replacing those there. A replica shows a space it does not hold by the names on the record derived for it; the records are listed and found nowhere else. A replica that keeps a group's log only to follow it in a space writes none for it. An AI agent's replica lists only the spaces it holds, as the names of the others are not for its AI agent.

**How a space reaches the user's replicas.** After each sync, a user's replica that is listed in the personal space, not revoked and not an AI agent's:

1. takes each space it lacks that the counting entries on its record give it, where its newest choice of the space in the personal space holds it, as when it asked, or it chose none and takes new spaces; never where that choice declined or dropped it. It opens the first key, keeps it if its hash is the one named, and makes the space, empty until it syncs it. It takes as the space's first change only one that an entry names, and refuses any other without rejecting it. Then it states a choice to hold each space it took (below), in one governing change of the personal space;
2. asks to be listed in each space it holds and is not listed in, unless it asked before, by stating on its own record in the personal space its listing for that space, owned by the member that the entry names;
3. revokes, in each space it is listed in, the keys of its member's replicas there that the personal space revokes, with a new key for the space, as a revocation does (section 4);
4. lists, in each space it is listed in, the user's replicas that asked to be: those whose records in the personal space hold a counting listing of their own key for the space, owned by this replica's member there, that verifies; whose key is not listed there yet; that are not revoked or an AI agent's in the personal space; and whose newest choice of the space there did not decline or drop it. It asserts the listing with the replica's key, encryption key and owner, as founding does, in a governing change wrapped with the space's first key, which is all that the new replica holds yet. The changes after it assert the replica's record, with the names of its app and device and its endpoint as the personal space has them, and its device's record in the space, derived as above. Then it gives the replica the space's keys (section 4);
5. gives each space it is listed in to every recovery code of the user that stands in the personal space (section 11) and has no entry of that space yet: an entry with the space's first key sealed to that code, in one governing change of the personal space, wrapped with its first key. So a code is given every space of the user's.

A replica syncs a space it holds but has nothing of yet with the user's other replicas that the personal space lists and that are neither revoked nor AI agents' ([Sync](sync.md#4-who-syncs)). Pairing grants only the personal space's keys ([Sync](sync.md#2-pairing)). A new replica takes the spaces its records give it after its first sync, whatever it says of new spaces, and asks to be listed in each as every replica does.

**Revoking.** A user's replica that revokes another (section 4) revokes it too in every space where it is listed, each with a new key. Where it could not, the user's other replicas listed there do so after their next sync (step 3 above).

**Secrets.** Each space has secrets keys of its own, set up and given as section 6 says ("Another space's secrets").

**Copies.** A new replica added by a copy's own keys (section 7) takes the copy's other spaces from the private copy, as a new computer does, before the copy's device is revoked: the private copy gives it every space as it pairs it, the new replica asks to be listed, and the private copy lists it, in syncs within the one program.

**Choices.** A device chooses whether it holds a space other than the personal one ([technical design](../Technical-design.md#1310-devices-that-choose-their-spaces)). A *choice* is the canonical encoding of `[space, record, key, number, holds, signature]` in base64url without padding, where:

- `record` is the device's record in the space, derived as above from the space and its verifying key `key`;
- `number` counts the device's choices of that space from 1;
- `holds` says whether it holds the space;
- `signature` is the key's, with the context `nibkeep space choice`, of the canonical encoding of `[space, record, key, number, holds]`.

The device states each choice as `org.nibkeep.space-choice` in a governing change, with a number one above the highest of its choices of that space that the personal space and the space state. It states it on its own record in the personal space, and, where it holds the space by its choices too and is listed there, on its record there, where [the log](log.md#8-which-changes-count) decides what it does. A standing choice not to hold the space ends the device there, as a removal ends a member's replica (section 9): the space's other replicas seal it no key and give the space a new one, and a new secrets key where it held them (section 6), and a sync sends it only what ended it ([Sync](sync.md#3-syncing)).

After each sync, a user's replica carries drops into each space where it is listed, or is a member through a group alone, with a role, if it is not revoked, holds the space by its choices, and is not an AI agent's. It states there each choice not to hold the space that a replica of its user, listed there, not revoked and not an AI agent's, states in the personal space on its own record, signed by its key of its own, that verifies and whose number is higher than that of that replica's standing choice there. A device that dropped a space comes back when a replica of its user that holds the space, once the person approves, states there the device's newest choice to hold it from the personal space, whose number is higher than that of its standing choice; it is then given every key made meanwhile (section 4). A choice of the personal space is refused. A device that drops a space as its person asks there states its choice only once its copies are elsewhere, and deletes the space afterwards, as [Storage](storage.md#17-dropping-a-space) says.

**Names.** A space other than the personal one may be renamed by an ordinary statement of its own entity's name that replaces its names; the personal space keeps its name.

**Entities in spaces.** A program chooses the space that each new entity goes to, by default the personal space. Listing and search cover every space a replica holds, and show which space holds each entity. A reference names an entity by its ID, whichever space holds it.

**Moving.** Sharing means moving ([6.7](../Design.md#67-spaces-members-and-devices)), and giving something to someone means moving it to their space ([technical design](../Technical-design.md#132-ownership)). A move takes each of these once, except those deleted or moved already:

- the entity, as merges make it canonical;
- the folders and lists that it holds, with their memberships and members, through every level of the folders and lists inside it;
- the files attached to any of them.

A folder holds what names it, or an entity merged into it, in `std.in-folder`; an ordered list, the memberships that name it so in `org.nibkeep.list`, with their items; an entity, the files that name it in `std.attached-to` and name nothing else that stays, deleted or moved entities aside. A membership moves only with its list. A file's origins (`std.origin-of`) and checkouts (`std.checkout-of`) that name it, or an entity merged into it, and are neither deleted nor moved already, go with it where their device (`std.found-on`, `std.checked-out-on`) is one of the mover's own on which a replica of the user's that is not revoked holds the new space, as its newest choice of it in the personal space says (above), and the content they recorded, if any, moves with the file. The others stay, and are purged with what stays behind.

Before it moves several, or takes one out of folders and lists that stay, an app shows how many go, and which folders and lists that stay hold some of them. A move first asserts, in the first space, `org.nibkeep.moved-into` on each entity it takes, referring to a new entity, and deletes nothing. Then it writes the new entities in the other space, one change for each:

- **Their statements,** under new IDs drawn in the order of the old ones. A form of a value names its first form by the new ID. A reference to an entity that moves along leads to its new one; one to an entity that moved to the other space already leads to that one there. A move does not carry whether they are deleted, merged or moved; nor, of a field whose last writer wins, more than the value it shows; nor a statement that puts one in a folder that stays, which finds it through its mark. Unless the person chooses otherwise, a move brings their history: the statements they and the entities merged into them have had, past ones too, each past one replaced in the change that writes it, so the current values, competing ones included, stay as they were. Each statement carried with its history holds the mover's note as qualifiers ([Data model](model.md#4-qualifiers)): the space it came from, the key that space recorded it by and when, and when it was replaced there. One that an earlier move carried keeps that move's note whole. History shows the statements as the mover's, written at the move, with the note as the mover's account, which only the first space proves, as it shows what a purge states again ([technical design](../Technical-design.md#64-purging)).
- **Their secret values,** unless the person leaves them behind: every value, current or past, sealed in the first space, or of a field secret there and written before the field was, sealed in the other space with its secrets key, as any secret value written there is. A move takes them only with the secrets of both spaces unlocked. While those of the first space are locked, it refuses an entity that may hold some: one that holds a value of a field secret there, or whose types list one. A field secret in the first space stays secret in the other: where the other space's types would leave it plain, the move first makes it secret for good there, by the governing statement of [Data model](model.md#9-secret-fields), in the personal space, in a space without members, or as an admin, and is refused otherwise ([technical design](../Technical-design.md#13-sharing)). Where the replica holds no secrets of the other space, it first sets them up there, as the first secret value written there does, which needs an admin's role and no other member's replica holding them, or the move is refused. Nothing is written before these checks. Values left behind stay with the entity in the first space.
- **The definitions of their types** as the first space defines them, made as careful as the other space's types so a field secret there stays secret, which add what the other space lacks, in changes of their own.
- **Their files' content:** the key of the sealed copy that the replica holds with a key of the kind, secret or ordinary, of the field that holds the content in the other space, wrapped for the other space once the copy was read whole, as a replica's spaces share their sealed blobs, reusing keys only within their kind ([Storage](storage.md#3-blobs)). Where the other space purged that copy, or the replica holds none of that kind, the content is sealed anew from a copy it holds or from where it was found on this device. Content that their history names is taken where the replica holds it. A purge in one space leaves the content readable through the other.

**Purging what stays behind.** Unless the person chooses otherwise, a move also asks that what it leaves in the first space be purged ([technical design](../Technical-design.md#131-spaces-and-moves)): with its mark, it asserts `org.nibkeep.purge-asked`, `true`, on each entity it takes. A move that keeps what it leaves takes back such a statement of an earlier move that was cut short, and no move carries it.

The replica that made the move purges in the first space once the new entity counts and another device holds it. It takes that to be so once a sync of the new entity's space with another device, started after the move, ends, or, where what stays holds content that moved, once the copies of that content in the new space are proven ([Storage policies](policies.md#7-removing-copies)). It purges every statement, current or past, of the entity, of the entities merged into it before the move, and of the origins and checkouts of a file that stayed, deleted ones too, that the mark's change builds on. It keeps the marks, `org.nibkeep.moved-into`, `org.nibkeep.purge-asked` and `org.nibkeep.merged-into`. It also keeps each secret value, sealed or of a field secret in the first space, unless it sees the new entity hold the same value in the same field, a reference leading where what it refers to moved, which needs the secrets of both spaces unlocked. It purges the content of its files that no statement that stays holds in a field of the same kind, secret or ordinary, of that entity or another, in a purge for each kind.

The mover's member purges what the [log](log.md#8-which-changes-count) lets them purge there: in the personal space, or as an admin, all of that; as an editor, only the statements of changes that their own replicas signed, and no content; as a viewer, or from a replica that the space does not list or revoked, nothing. An admin of the first space whose replica holds the new space sees the request where the new entity counts there with the values that the old one shows: each field that a move carries has on the new one a value equal to one of the old one's, a reference leading where the old one's moved. Only where that holds does the admin purge the rest, as the mover would. Nothing is purged just because a mark asks for it.

Before a move, a program shows the members of the first space who are not members of the new one, who no longer see what moves once it is purged, and says, for an editor, that they lose it only once an admin purges the rest. It also shows the members of the new space who are not members of the first, who see what moves for the first time, with the history it brings. The marks stay, so links still find the new entity. An edit that reaches the first space after the move needs a purge of its own.

A mark whose entity a replica holds nowhere is passed over, so a move cut short leaves the entities where they were. A replica that holds the space where an entity is now finds it there by any old ID, follows moves onward, finds it by its name there, lists it there alone, and names the links to it by it. A program that chose the old space finds the old entity there, to show or purge it. On the new entity, a replica shows the links of its other spaces that lead to the old one, except from entities whose new ones link to it there, as what moved along does. A replica that does not hold the new space shows the old entity as it was, marked as moved. The first space keeps the history it had. An entity moved once moves no further from there. Two moves of one entity at the same time make two entities, and links lead to the one with the smallest ID. A move refuses the library's own records, definitions, storage policies and rules, a tree, what is in one, and a folder or a list that holds them, as a tree moves only whole. AI agents do not move entities, as the field is NibKeep's own (section 5).

## 9. Members and invitations

A space with members is shared by inviting other users to it ([technical design](../Technical-design.md#13-sharing)). Each member has a record there (section 8) and a role, which decides which of their changes count ([Log](log.md#8-which-changes-count)):

- `viewer` sees everything and changes only their own records: the member's, and those of their replicas and devices;
- `editor` also changes everything but other members' records;
- `admin` may do anything, such as invite others and give roles;
- `none` is for a member who left or was removed.

A member's role now is the lowest of those that the counting governing changes give them and that no other of them builds on.

**Who is who.** A member is a record, not a user. Two records that name one user ID are two members, each with a role of their own. Before confirming, an admin who invites is told of the members whose records name the same user ID, with their devices. A user who left and comes back is a new member, with a new record.

**An invitation** runs as section 7 of the [sync specification](sync.md#7-invitations) says. Once the joiner holds the space, the admin's replica commits the new member, as founding a space commits its founder (section 8). A governing change asserts, on the member's new record, the user's ID as `org.nibkeep.user-id` and the role given as `org.nibkeep.role`; and, on the joiner's record, derived from the space and its key, the joiner's key, its encryption key, the member as its owner and the listing that the joiner's key signed. Then come the member's type `org.nibkeep.user` and the user's name; the joiner's record with its app's name, its device and its endpoint ID; and its device's record, derived the same way, with the device's name. The log counts such a change only from an admin, and only for a member record that no change it builds on names. A device whose key the space lists already, as one whose first sync failed, comes back as the member its listing names, which gets the role anew, as a key keeps the member of its first listing. The joiner then gives the space to its user's other replicas through the personal space. They ask to be listed, and a replica of the member listed there lists them, as for a space of one's own (section 8).

**Roles.** An admin gives a member another role in a governing change that asserts the role on the member's record, replacing its current statements. A program refuses one that would leave the space without an admin, as the log counts none. While a space has a single admin, a program that invites suggests making the new member a second admin; a personal space never suggests one.

**Leaving and removing.** A member leaves by giving their own record the role `none`, and an admin removes a member by giving theirs `none`, each in a governing change that replaces the current statements of the role ([technical design](../Technical-design.md#13-sharing)). A program refuses the only admin's leaving while other members remain, and asks them to make another an admin first, as the log would count none. The last member's leaving closes the space.

Leaving or being removed ends every replica of the member in the space. What they did without knowing of it is set aside, for an admin to review ([Log](log.md#8-which-changes-count)). A replica whose member left or was removed changes nothing there after, lists none of its user's other replicas there, gives the space to none of them, and keeps what it holds, read only. No replica gives such replicas keys (section 4). A sync sends such a replica only the changes that ended it and what they build on, and no keys or files, and takes from it only those of its own changes that build on none of them ([Sync](sync.md#3-syncing)). The replica that removes a member, or that stops allowing AI agents where one is listed, gives the space a new key at once, sealed to the replicas that remain. The others make one as they learn of a departure, if their newest key is not safe.

A device of the former member that an admin's device invites back before it learned of the departure refuses the invitation and asks for one after the two have synced. Of two admins who remove each other, the one who became an admin first stays, as for any two who lower each other's roles, and each receives the removal that counts. A replica of a former member that an admin invites again comes back as a new member, with a record of its own, keeping what it holds of the space: the invitation lists its key again, for the new member. A program that finds a member by name prefers the one with a role.

**Links to people.** A member is linked to a person in the space, such as Olga in the family tree, when an admin and the member agree ([users and people](../Design.md#610-users-people-and-devices)). Each states `org.nibkeep.linked-person` on the member's record, a reference to the person, and replaces only its own side's statements, so the other's stays. A statement counts as the member's own if one of the member's replicas signed its change, by the counting listings, and otherwise as an admin's, as only those count on a member's record. The link holds when the latest statement of each side names the same person, not deleted. An admin's own statement counts for both sides while they are an admin, so an admin who loses the role keeps the link only if another admin agrees. A link names a person, an entity of the type `std.person` in the space (the standard vocabulary's, [Data model](model.md#1-names)), never a member's record. Programs write it only through the link's own operation, never as a plain edit of the field, which would replace the other side's statement too. An invitation may name the person: the admin's replica states its side with the new member's record, and the joiner states its own once the user agrees. History names a member by the person their link holds to in that space, and otherwise by their own name there.

**Syncing with other members.** A replica syncs each space with members with the replicas that its counting listings give the other members, as with the user's own ([Sync](sync.md#4-who-syncs)). The personal spaces stay apart, as only the user's own replicas are listed there.

**Claims to the admin role.** A direct member who is an editor claims the admin role of a space on their own record, when its admins are gone ([Log](log.md#10-claims-to-the-admin-role)); a program says first what claiming does. After each sync, each replica in a space shows that it saw each counting claim and rejection there of another member's, which it has not shown yet, with `org.nibkeep.seen` on its own record. A program lists a space's claims, with when each was made, first seen, takes effect and is settled, and whether a rejection voids it. Before acting as an admin, it decides what a claim gives its user now by the latest wall clock time it was given: the computer's when the library opened, and each one a change or a sync gave it since. An admin rejects a member's claims, except a settled claim, which no rejection undoes. An admin whose own claim took effect less than 30 days ago cannot reject one, nor purge, accept, make an admin or lower one. Each of these actions goes by the latest of the wall clock time it was given and those before. Once a claim of its member's is settled, the claimant's replica, while its member is an editor, states `admin` on its own record, as the rules of never being without an admin go by the records.

## 10. Groups

A group is a space with members and no data of its own ([Technical design](../Technical-design.md#138-groups)), whose own entity is of the type `org.nibkeep.group` instead of `org.nibkeep.space`. It is founded as a space is (section 8), and its first change also asserts `org.nibkeep.space-kind`, `group`, on its own entity, which alone says that it is a group. Its members are invited, given roles, and leave or are removed as a space's (section 9). Every change of a group, governing or not, is wrapped with its first key, which never changes. A program writes no entity of its own there, and moves none there. A group is a member of spaces and of other groups alike: a group inside a group reaches every space the outer group is in, at every level. The [log](log.md#9-groups) decides what a group gives in a space.

**Adding a group to a space.** An admin of the space who is a member of the group adds it, as an editor or a viewer, in a governing change that asserts, on a new record, `org.nibkeep.group`, naming the group, its first change and the hash of its first key ([Log](log.md#9-groups)), which is the *addition*, and the role. An admin of the space takes a group out with the role `none` on its record, as a removal does. A program refuses to make a group's record an admin's, and to add a group to itself, or to a space or group that the group holds at some level. A group is added to another group the same way, by an admin of the outer group. In the same step, the admin asks in the group, with a governing `org.nibkeep.join-request` statement on the group's own entity, which any member may make. Its value is the canonical encoding of `[space, root, addition, names]` in base64url without padding, where `root` is the space's first change. For each replica of the group's admins that is not revoked, `names` holds its record and the space's name sealed to its encryption key with the context `nibkeep 2026-11 space names` and the associated data `[space, record]`. A replica whose member is an admin of the group agrees at once.

**Agreeing and withdrawing.** An admin of the group agrees with `org.nibkeep.joined`, `[space, root, addition]` as a request names them, on the group's own entity, and withdraws, for good, with `org.nibkeep.withdrawn` in the same form. A program lists the requests with the spaces' names where they are sealed to its replica.

**Anchors.** A replica that is in a space, by any path, and holds the log of a group that reaches the space anchors the group's changes there, after each change it makes to the group and after each sync. It does so whenever the group's governing changes that no other builds on are not all among what the space's counting anchors name. A group reaches the space, by the replica's copies of the logs, if the space adds it with a role and it agreed to that addition, or, at every level, if a group that reaches the space adds it so. A replica anchors no group that holds the space at some level. Its anchor is an `org.nibkeep.anchor` statement naming those changes, on the record in the space of the group, or of the group in the space through which it reaches the space. Where no counting change of the space gives the group's first key yet, the same change also asserts `org.nibkeep.group-key` there: the canonical encoding of `[group, root, key]` in base64url without padding, with the key's 32 bytes, inside the change, which the space's key wraps.

**Following.** A replica of a space keeps the log of each group that the space adds, and of each group that those add, at every level, as a space of its own. It keeps it as a member of the group, or else read only, with the first key that an `org.nibkeep.group-key` statement in a space it holds gives, whose hash a record of a space or a group it holds names with the group and its first change. It takes as the group's first change only one that a record of the group names. Each time it opens the library, after each sync, and after each change it makes to a group, each space follows the groups it adds, at every level, except itself, as the replica's copies of their logs say ([Log](log.md#9-groups)).

**Giving the space to the group's members.** After each sync, a replica whose member is an admin of a group, as an entry counts from no other member ([Log](log.md#8-which-changes-count)), gives each space it holds and is in, that adds the group with a role, and that the group agreed to join and did not withdraw from. It gives it to every replica of the group's members, also of its members through the groups inside it, that remains there, is not an AI agent's and lacks an entry of it. The entry is an `org.nibkeep.space-entry` statement on that replica's record in the group, derived from the group and its key, as the personal space gives a user's spaces (section 8). It names the space's first change, with the member the replica is of in the group, or in the group inside it that lists it. The replica gives the space alike to each recovery code that the group gives its keys to (section 11), on the code's record in the group, with the code's member there. A replica takes such an entry on its own record in a group it is in only for a space that the group agreed to join, naming that first change, and did not withdraw from. It takes it as a space made elsewhere: where its newest choice of the space in the personal space holds it, or it chose none and takes new spaces, never where it declined or dropped it (section 8). It keeps the space, empty until it syncs it, takes as its first change only the one named, and states a choice to hold it.

**Keys.** The replicas that a group in a space lists, as the log says, get the space's keys on their records there, derived from the space and their keys (section 8). The keys are sealed to the encryption keys that their records in the group that lists them state, as the space's own replicas' are (section 4), and they take them so. A departure through a group, at any level, gives the space a new key once an anchor names it, as a removal does (section 9): a member's removal from a group, a group's from the group it is in, a revocation of a key, or a withdrawal from the space or a group, as the log names them.

**Direct members.** An admin of a space makes a member through a group a direct member, such as to make them an admin, with no code. In a governing change, it makes a new member's record with the user ID and the role, and `org.nibkeep.made-for` naming one of the member's keys in the group, whose user ID and name the record copies. The record is never made for an AI agent's key. Once the person confirms, the replica they confirm on lists itself on the record, as the log allows a member's replica on a record made for one of their keys. The user's other replicas list themselves on it after a sync, once a replica of their user is listed there. A replica lists itself on a record once only, and says so if the log refused it. Their records in the space and the group are then one person, with the higher role (section 9).

**Keeping out and leaving.** An admin keeps a member through a group out of a space by stating `org.nibkeep.kept-out`, `true`, on the record in the space derived from the space and each key of the member's replicas in the group, and lets them back with `false`, each replacing what the record says now. A member through a group leaves a space and stays in the group by stating `true` on their own key's record, which every member may do; `false` needs an admin. A member who leaves, or whom an admin removes, and who is in the space through a group too, is kept out the same way, in the same change as the role `none`. They are kept out by the keys of their replicas that groups list, and the key a record made for them names, so removing such a record before they confirm keeps them out too. A replica that is not listed yet on its user's record leaves by that record. A removal from the space ends no replica of a person whom a group still gives a role. Keeping out a person whom nothing else gives a role ends their replicas in the space, as a removal does (section 9): the space gets a new key, their replicas are sent only what ended them, and they take only keys given before. Once let back in, they are given the keys again.

**Members.** A program lists a space's groups apart from its members: each with its role, whether it agreed, and, where the replica holds its log, its name, its members with their roles in the group, and the groups inside it, the same way, at every level. History names a member through a group as the first group by ID that lists their key, and whose log the replica holds, names them.

## 11. Recovery codes

A *recovery code* is a key that a person keeps on paper, from which a recovery key and two decryption keys are derived ([Cryptography](crypto.md#8-recovery-codes), [technical design](../Technical-design.md#111-recovery-codes)). A code is not a replica: no key of it is listed, and it signs no change. Its member's replicas name it, and seal the space's keys to it as they do to each other. This version names a code in the personal space and in every space and group that its user's replicas are listed in, and gives it those spaces and their keys. It keeps the personal space's first key for the code in a recovery file in each replica's folder and each backup, and revokes codes. A new replica recovers by a code, from a backup or from a library on the computer that no longer unlocks, the personal space and the user's other spaces and groups that the source holds, and lists itself in each by the code or through a group. [Known limits](../Known-limits.md#recovery-codes) says what is still to come.

**A code's record** in a space is an `org.nibkeep.recovery-code` entity whose ID is derived from the space, the member whose code it is, and the recovery key: the first 16 bytes of the BLAKE3 key derived with the context `nibkeep 2026-11 recovery records` from the space's ID followed by the member's ID and the recovery key's 32 bytes, as a version 4 UUID. The member is the user's own entity in a personal space. In a space with members, it is the member's record: one of theirs in the space itself, or, for a member through a group alone, their record in the group that lists their key, by which history names their changes (section 10).

**Naming a code.** A replica names a code once the person has typed it back, in a governing change that asserts `org.nibkeep.recovery-key` on the code's record. The value is the canonical encoding of `[member, key, encryption, secrets encryption, signature]` in base64url without padding:

- the member;
- the recovery key, as a verifying key;
- the code's encryption key and its secrets encryption key ([Cryptography](crypto.md#5-sealing-to-a-public-key));
- the recovery key's signature, with the context `nibkeep recovery key`, of the canonical encoding of `[encryption hash, secrets encryption hash]`, the BLAKE3 hashes of the two encryption keys' 1,216 bytes, each written as a hash.

The signature names no space and no member, so the same statement serves every space. In the personal space, the same change also asserts `org.nibkeep.recovery-entry` on the code's record, which holds what the recovery file's entry for the code names (below). Its value is the canonical encoding of `[space, member, root, key hash, recovery key, signature]` in base64url without padding:

- the personal space;
- the member that the statement of `org.nibkeep.recovery-key` names;
- the ID of the space's first change;
- the first key's hash;
- the recovery key;
- the recovery key's signature, with the context `nibkeep recovery entry`, of the canonical encoding of `[space, member, root, key hash]`.

A change after it gives the record its type and its name: the *name* of the recovery key.

**Which codes a space has.** A space's codes are those that counting `org.nibkeep.recovery-key` statements name with a signature that verifies, each on the record derived from the space, the member that the statement names, and its recovery key. Of several such statements on one record, the earliest in the order of the [log](log.md#8-which-changes-count) counts. Any other statement names nothing. A code's entries in a personal space are those that counting `org.nibkeep.recovery-entry` statements state on its record, for that space and its recovery key, with a signature that verifies, whichever replica states them. In a space with members, a statement of a code counts only from a replica of the member whose record for the code it is on ([Log](log.md#8-which-changes-count)); in a personal space, every replica is the user's. An AI agent's replica names no code, as its governing changes never count (section 5). The replica that made a code, or carried it into a space, is the one whose key signed the change, never what a record says.

**Keys.** A code that stands is given the space's keys as a replica that remains is (section 4), if, in a space with members, its member has a role other than `none` there: directly, or, for a member's record in a group, through one of the keys that the groups list on it. Each key but key 0 is given in an `org.nibkeep.space-key` statement on the code's record, sealed to the code's encryption key with the code's record as the replica in the associated data.

**In every space.** After each sync, and as it names or revokes a code, a user's replica that is not an AI agent's carries the codes of the personal space into each other space and group that it is listed in and that its member did not leave. It is listed there for a member of that space itself or, failing one, through a group that gives it a role there. There it:

- names each code that stands in the personal space and that the space does not name yet on a record of its member's that gives it a role there. It names it on the record derived from that space, its member's record and the recovery key, with the same statement but for the member;
- revokes, as below, each code that the personal space names as revoked, on each record of its member's for the code that the space names as standing, each in a change of its own.

Its member's record is its record in the space itself, or else its record in the group by which history names its changes, with a role there (section 10). Each user's replicas carry their own codes, as only a member's own replicas name or revoke that member's. A replica names a code on a record, and revokes it there, once only, whether its statement counts or not. A code named so is given that space's keys as above. The personal space also gives each of the user's other spaces to each code that stands there, as to the user's replicas (section 8): an `org.nibkeep.space-entry` statement on the code's record in the personal space, with the space's first key sealed to the code's encryption key and the code's record as the replica in the associated data.

**The secrets.** A code holds the secrets only if a person chose so, on a replica that holds them, with them unlocked, as the code was named or later. That replica gives the code each secrets key of the personal space that it holds and gives out, in `org.nibkeep.secrets-key` statements on the code's record (section 6), sealed to the code's secrets encryption key, with the code's record as the replica in the associated data and in the link. The first is linked with itself, so every replica that holds that key knows that the code holds the secrets. A code asks nobody, and states nothing: it has no `org.nibkeep.secrets-from`, and secrets keys are sealed to the encryption key that it signed. A replica that gives secrets keys to those known to hold them (section 6) counts a code that stands, and whose member has a role, as known to hold a space's secrets if:

- it gave the code a secrets key there itself;
- a counting gift to the code's secrets encryption key carries a link that a secrets key it holds checks, of the same space or the personal one; or
- in a space other than the personal one, the code of the same recovery key is known to hold the personal space's, as a replica of the same user is.

A counting revocation of a code that a statement gave a secrets key is a departure after which the secrets need a new key (section 6).

**A new code replaces those before it.** Of the person's codes that stand in the personal space, the newest, by its statement's timestamp and then its ID, replaces the others. After each sync, after each update of a backup, and as a code is named, a user's replica that is not an AI agent's revokes each code that another replaces, as below, once every backup of the user carries the newest (below), or at once where the person says so. Until then the person keeps the old code's paper. With no backup, the newest replaces the others at once. Revoking a device names the person's codes that stand and that its replicas made, as the key that signed each one's statement says, and revokes them too where the person says so.

**Revoking a code.** A replica of the code's member revokes it in a governing change that asserts `org.nibkeep.recovery-revoked` on the code's record, with the recovery key in the form of `org.nibkeep.signing-key`, and gives the space a new key, sealed to the replicas that remain and the codes that still stand. A code is revoked once a counting statement on its record names its recovery key so, and a revocation is final. The field is not the one that revokes a replica's key: a statement of it revokes no replica, whatever key it names. A statement on one member's record for a code says nothing of another member's.

**The recovery file.** The personal space's first key cannot come from the log, whose governing changes it wraps. So while a code stands in the personal space, each replica of the user that is not an AI agent's keeps the file `recovery.cbor` in its folder ([Storage](storage.md#1-layout)). It is the CBOR array `[1, codes, check]`:

- `codes` holds, for each code that stands, sorted by its record, `[record, entry, signature]`:
  - the code's record in the personal space;
  - the personal space's entry for it, as section 8 gives a space to a replica, as the CBOR array `[space, member, root, key hash, sealed key]`: the personal space, the member that the code's statement names, the ID of the space's first change, the first key's hash, and the first key sealed to the code's encryption key, with the context `nibkeep 2026-11 first keys` and the code's record as the replica in the associated data `[space, 0, record]`;
  - the signature of the code's entry that names the same space, member, first change and first key's hash, as the space states it on the code's record;
- `check` is the BLAKE3 hash of the canonical encoding of `codes`, so a file damaged on its drive does not read.

A code without such an entry, as one that an earlier version named, gets none in the file. As a code is named or revoked, and after each sync, a replica writes the file anew, whole, as section 1 of the storage specification writes a file, where it does not read, or where its entries are not one for each such code that stands, each naming the space, the code's member, the first change, the first key's hash and the signature as above. It deletes the file once no code stands. Each backup of the user holds the same file, which the computer that updates it writes in the same way, with the personal space's changes and keys ([Storage](storage.md#6-backups)).

A program opens the file with a code from the entry on the record derived from the entry's space, its member and the code's recovery key. It does so only if the code's recovery key verifies the entry's signature, with the context `nibkeep recovery entry`, of the entry's `[space, member, root, key hash]`, and the key it opens to has the hash that the entry names. A program says that the file was changed where it holds an entry on the code's record whose signature does not verify, or that does not open to the key that it names.

**Which backups carry a code.** A backup carries a code that stands once its latest account in the personal space ([Log](log.md#11-accounts-of-copies)) names heads that are, or build on, the change that named the code there. `nib recovery list` names, for each code that stands, the backups that carry it and those still to update.

**Checking a code.** On a device that works, a program checks a code that a person types:

- whether the personal space names it, and whether it stands;
- in each space that names it, which of the keys that the replica holds and that are given out it opens, as the `org.nibkeep.space-key` statements on its record give them;
- whether the personal space's entry of that space opens with the code to the space's first key;
- where the replica's secrets are unlocked, which of the secrets keys that it holds and that are given out the code opens.

**The person's codes** are all those that their personal space names, whichever member a statement names there, as every replica of that space is the user's: each is given the space's keys, so each is listed, and revoked by its name. A code's record is one of the library's own records, as a replica's is: nothing merges or moves it, and an export of current values leaves it out.

**Recovering.** A program recovers a library on a new device, as a new replica, from a code that the person types and a folder that holds a backup of theirs ([technical design](../Technical-design.md#111-recovery-codes)):

1. Before it makes anything, it opens with the code the personal space's first key from the backup's recovery file, as above. It refuses a folder whose `backup.cbor` names no backup, that holds no recovery file, or whose file does not open with the code, as when the code did not sign its entry.
2. The new replica makes its keys (section 3). Its library file records the user that the entry names, a new device and a new replica, and the personal space. Its key file holds the personal space's first key alone, and its space is told that the entry's first change founds it.
3. It takes in what the backup holds of the personal space, as an update of a backup takes in its packs ([Storage](storage.md#6-backups)). It refuses a code that the space does not name, on the record derived from the space, the entry's member and the code's recovery key, or that the space revoked.
4. It takes the space keys that `org.nibkeep.space-key` statements on the code's record seal to the code, as a replica takes those sealed to it (section 4), opening them with the code's decryption key, until none is left to take.
5. It lists itself, in a governing change that builds on every change it holds and is wrapped with key 0. On its new record, the change asserts its verifying key, its encryption key, the entry's member as its owner, and its *recovery listing* as `org.nibkeep.recovery-listing`: the canonical encoding of `[space, record, owner, encryption, key, recovery key, signature]` in base64url without padding. There `encryption` is the BLAKE3 hash, written as a hash, of the 1,216 bytes of its encryption key, `key` its verifying key, and the signature, with the context `nibkeep recovery listing`, is the recovery key's of the canonical encoding of `[space, record, owner, encryption, key]`. A change after it gives the record and its device their types and names, its device and its endpoint, as section 3 does.
6. It takes the user's other spaces and groups. Each that an `org.nibkeep.space-entry` gives the code, on one of the code's records in the personal space, or in a group that the replica holds, for a space that the group agreed to join (section 10), it takes as section 8 takes a space from an entry. It opens the first key with the code's decryption key and the code's record as the replica, and expects the entry's first change. It also takes the logs of the groups that the spaces it holds add (section 10). It takes in what the backup holds of each, after each follows the groups it holds, and the keys sealed to the code on each of the code's records there, whichever member each names. It goes round again until a round takes nothing new, as a group's entries open once its keys do, and a space takes its groups' members' changes once it follows them. A space or group given to the code of which the backup holds nothing does not come back: the replica names it, and removes it with its key, except a group that a space it holds adds, whose log it keeps, empty, to follow it.
7. In each space with members that the personal space gives the code, where the code stands on the record of the member that the entry names and that member has a role, it lists itself on that member's record. It does so in a governing change wrapped with key 0, as section 8 lists a replica there, with its own listing and its recovery listing for that space and member. Where that listing counts, a change after it names the record and its device; where it does not, the space stays as the backup held it, to be read. A space that the user reaches through a group alone lists it through the group, once the replica has listed itself in the group.
8. It revokes every other replica of the user that is not revoked, except those that the person keeps as devices still at hand, in every space where they are listed (section 4). It revokes in any case the replica of a library that no longer unlocks that it reads, and one that a recovery cut short left in the same place. With them, as section 4 says, go the replicas that they added in the spaces and groups it took and that the personal space does not list.
9. In each space that does not list it yet and that a group which lists it reaches, it anchors the groups' changes (section 10), so the space lists it through the group and learns of the revocations there.
10. It settles its keys, and updates the backup, if the space still names it.

Its folder holds the file `recovering` from when it is made until all this is done ([Storage](storage.md#1-layout)). Until then, the library does not open, and a recovery run again removes that replica, with its keystore keys, and starts over. Nobody knows the replica, as it syncs only after. A listing that an update cut short left on the backup is one more replica of the user's, which the next recovery in the same place revokes in any case, and one elsewhere unless the person keeps it.

**A replica listed by a code** is listed as the [log](log.md#8-which-changes-count) says. Its listing counts once a counting change that it builds on names the code for the listing's owner, and every counting revocation of the code builds on it. It counts as added at that change, and as listed through a code, as does every replica that it, or another listed through a code, lists. Of two replicas that revoke each other, one listed through a code loses to one that was not ([technical design](../Technical-design.md#111-recovery-codes)). A code lists no AI agent's replica: a change that marks the record as one lists nothing by the code. A replica takes such a listing from another replica, although nothing listed its key, where it can read the listing with the keys it holds and a governing change that it can read names the code. In a space with members, the change carries the replica's own listing too, and the code's statement counts only from a replica of the listing's owner. A replica listed by a code has its member's role at once, an admin's too. A replica that listed itself by a code shows its listings in the hello of each sync that it starts, to the replica it connects to and for the spaces they share, so one that does not know it yet takes it ([Sync](sync.md#3-syncing)).
