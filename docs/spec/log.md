# Log

- **Version:** 1

Each space keeps a log of its changes ([6.5](../Design.md#65-history-and-deletion)). A change is a set of operations ([Data model](model.md#5-operations)) that one replica made at one time, signed by the replica, with its payload sealed under a key of its own that the space's key opens. This specification describes changes, how a replica accepts them, and the history and ordered lists built on them. The reasons for the choices are in the [technical design](../Technical-design.md#61-changes). Structures are written in canonical CBOR as described in [Encoding](encoding.md).

Every change has a key of its own, so that any value can be purged ([technical design](../Technical-design.md#64-purging)): the change's header holds the hashes of its sealed payload and key and what it purges, a change is accepted on its header alone, and its payload is applied once it is there with its key. A purge destroys the keys and payloads of the changes that held a value, and states again what else they held (section 7).

## 1. Changes

A change is the CBOR array `[1, header, signature]`:

| Item | Content |
| --- | --- |
| `1` | Suite 1: the format described here |
| `header` | The array described below |
| `signature` | The author's signature ([Cryptography](crypto.md#4-signatures)) of the canonical encoding of the header, with the context `nibkeep change` |

The header is the array `[space, epoch, author, parents, timestamp, kind, payload hash, key hash, sealed, purges]`, followed by `restores` in a change that restores anything (section 7):

| Item | Content |
| --- | --- |
| `space` | The ID of the space |
| `epoch` | The number of the space key that wraps the change's key: 0 for the space's first key, and a random number for each new key ([Identity](identity.md#4-revoking-replicas)). New changes use the newest key, but governing changes, which use key 0 (section 8); replicas keep older keys to read older changes |
| `author` | The verifying key of the replica that made the change |
| `parents` | The IDs of the changes that the author's log ended with, its *heads*, when the author made the change, but that a governing change that revokes a replica or sets a role leaves out what builds on a governing change whose payload the author has not read (section 8); sorted by their bytes, without duplicates |
| `timestamp` | The system time of the change ([Time](time.md#3-system-time)) |
| `kind` | `0` for an ordinary change, `1` for a change that governs the space (below) |
| `payload hash` | The hash of the sealed payload's canonical encoding |
| `key hash` | The hash of the change key (below) |
| `sealed` | The secret statements that the payload seals: an array of `[id, record key hash]`, sorted by ID, without duplicates, where `record key hash` is the hash of the statement's record key (section 5) |
| `purges` | What the change purges: the array `[changes, statements, blobs]` of the IDs of changes, the IDs of secret statements, and the sealed hashes of blobs, each sorted by its bytes, without duplicates |
| `restores` | Only in a change that restores, of what purges destroyed: an array of the same form as `purges`, of which not all three are empty. A header with an empty `restores` is not a change's |

**Change IDs.** A change's ID is the BLAKE3 hash of its canonical encoding, written as a hash ([Encoding](encoding.md)).

**Change keys.** The payload of each change (section 5) is sealed in an envelope ([Cryptography](crypto.md#2-envelopes)) with a random key of its own, the *change key*, with the associated data `[space, key hash]`. The change key is wrapped with the key derived from the space key of the change's epoch with the context `nibkeep 2026-10 change keys`, with the associated data `[space, change ID]`, so that it opens for no other change. A *sealed payload* and a *wrapped change key* are each an envelope in CBOR. Neither is part of the change: both are stored and travel beside it, so that purging can delete them while the change, and every hash that names it, stays.

**Key hashes.** The hash of a change key or a record key is the BLAKE3 hash, written as a hash, of the 32 bytes of the key derived from it with the context `nibkeep 2026-10 key hashes`. The cipher of envelopes does not commit to its key, so without these hashes a replica could seal one payload, or one secret value, that opens to different contents under two keys, and send each key to different replicas. A key that is not the one whose hash the header holds is dropped, and so is a sealed payload whose hash is not the header's.

**Governing the space.** Whether a change may be made, or may purge, is decided from the space's members, their roles and their replicas' keys ([6.10](../Design.md#610-users-people-and-devices)), so every replica must read them alike. The statements that set them are of the fields `org.nibkeep.signing-key`, `org.nibkeep.encryption-key`, `org.nibkeep.owner`, `org.nibkeep.revoked`, `org.nibkeep.space-key`, `org.nibkeep.accepted`, `org.nibkeep.ai-agent`, `org.nibkeep.secret-field`, `org.nibkeep.secrets-encryption-key`, `org.nibkeep.secrets-from`, `org.nibkeep.secrets-key`, `org.nibkeep.role`, `org.nibkeep.user-id`, `org.nibkeep.listing`, `org.nibkeep.space-entry`, `org.nibkeep.ai-agents`, `org.nibkeep.group`, `org.nibkeep.anchor`, `org.nibkeep.joined`, `org.nibkeep.withdrawn`, `org.nibkeep.join-request`, `org.nibkeep.group-key`, `org.nibkeep.space-kind`, `org.nibkeep.made-for`, `org.nibkeep.kept-out`, `org.nibkeep.claim`, `org.nibkeep.rejected`, `org.nibkeep.seen`, `org.nibkeep.recovery-key`, `org.nibkeep.recovery-revoked`, `org.nibkeep.recovery-listing`, `org.nibkeep.recovery-entry`, `org.nibkeep.space-choice` and `org.nibkeep.new-spaces` ([Identity](identity.md), sections 8, 9 and 11). A change of kind `1` holds only statements of these fields and retractions, and seals and purges nothing; a change of kind `0` holds no statement of these fields. A change of kind `1` may also state a field whose name starts with `org.nibkeep.` and that this version does not know, which a later version may govern with: the statement is kept, and has no effect here. NibKeep's other fields, those this version knows, never stand in a change of kind `1`, as such a change is never purged. Those are fixed at version 1 for every later version: a field of NibKeep's own that a later version adds, whether it governs or not, never makes a change of kind `1` add nothing, so that older and newer engines decide such a change alike. A change of kind `1` is never purged. A replica that makes a change also counts as governing what retracts or replaces a statement of these fields that it holds; whether a change it receives does so depends on statements that may not have arrived, so replicas check it once members and roles decide who may govern.

## 2. Accepting changes

A replica accepts a change from another replica after checking, in this order, that:

1. the change has the form described above;
2. its space is the log's space;
3. its signature is valid for its author;
4. if it governs the space, it seals and purges nothing, and its epoch is 0 (section 8): one of another epoch is rejected for good, with every change that builds on it, as the header alone decides;
5. its timestamp is not too far ahead of the wall clock of the replica's device ([Time](time.md#3-system-time));
6. none of its parents was rejected;
7. if it has no parents, in a space whose first change must govern it, as every space of NibKeep: it governs the space, and the log holds no accepted change yet; and if the replica was told which change founded the space, as what gave it the space's first key tells it: an entry of the personal space ([Identity](identity.md#8-spaces-of-ones-own)), an invitation, an entry in a group, or, for a group's own log, a space's record of the group; it is that change, or one of those changes where several tell it. Any other change without parents is then refused, without being rejected, so that the real first change is taken when it comes.

Whether the author may write to the space decides whether the change counts, once it is accepted (section 8).

A change whose parents have not all been accepted waits until they have. A replica may limit how many changes wait, and refuse more until their parents arrive. Once its parents are accepted, a change's timestamp must be later than theirs, and what it purges must be in changes it builds on: the changes it purges must be its ancestors and of kind `0`, and the statements it purges must be sealed in its ancestors (section 5). A change that fails these checks is rejected for good, and so is every change that builds on it: the checks depend only on the change's header and the headers of the changes it builds on, so every replica decides the same, and none needs to ask for such changes again.

A change is accepted on its header alone, and every replica acts at once on what its header says: the statements it seals and what it purges. Its operations, and each sealed statement that the replica can open (section 5), are applied, with the change's timestamp as the time they were recorded ([Data model](model.md#6-current-values)), once its sealed payload and a wrapped key that opens to its change key are there, in whichever order they arrive. Until then the change adds nothing else. A payload that opens but does not have the form of section 5, or seals other statements than the header names, or does not fit the change's kind, or states again what came from a change it does not build on (section 7), adds nothing, for good. Only once a change is accepted does the replica's clock take its timestamp into account. Whatever order changes, payloads and keys arrive in, every replica decides the same.

A replica that lacks the space key of a change's epoch keeps a few of the change's wrapped keys, since it cannot tell which is good, and applies the change once it gets that space key.

## 3. History

The *heads* of a log are the changes that no other change names as a parent. A new change names the heads as its parents, so the changes form a graph in which every change comes after everything its author had seen. Changes stay in the log for good.

**As of.** The state of a space as of a system time is the result of applying the changes whose timestamps are at most that time, as far as they were not purged: what a purge states again shows from the purge on (section 7). Because every change is later than its parents, these changes include all of their parents: no change appears without the changes it builds on. Timestamps are what the authors' replicas claim, though. A member could backdate a change, but not to before the changes it builds on.

**Attribution.** The author of a statement is the author of the change that first asserted it: the one with the earliest timestamp, and of changes with the same timestamp, the one with the smallest ID. A statement that a purge stated again is attributed to the purge's author.

## 4. Ordered lists

A list is an entity whose items belong to it through *memberships*: entities of type `org.nibkeep.membership` with these fields ([6.2](../Design.md#62-relationships)):

| Field | Value | Multiplicity |
| --- | --- | --- |
| `org.nibkeep.list` | Reference to the list; a role | One |
| `org.nibkeep.item` | Reference to the item; a role | One |
| `org.nibkeep.position` | Text: a position key | Last writer wins |

Other facts about the membership, such as who added the item or recommended it, are fields of the membership as well.

**Position keys** are non-empty strings of the 62 characters `0`–`9`, `A`–`Z` and `a`–`z` that do not end in `0`. They are compared by their bytes. Between two different keys there is always room for another, so moving an item needs a new key for that item only.

**Order.** The items of a list are the entities of type `org.nibkeep.membership` that refer to it and are not deleted, sorted by position key; memberships without a valid key come first, and memberships with equal keys are sorted by their IDs.

**Moving** an item gives its membership a key between those of its new neighbours. If several memberships after the new place share the key of the one before it, which happens only when items were placed concurrently, they get new keys as well, in their order.

If two replicas move the same item at the same time, the key recorded last counts, so the item appears once, at one of the two places. Whatever happens concurrently, no item is lost or listed twice.

## 5. Payloads and secret fields

The values of secret fields are encrypted twice ([6.9](../Design.md#69-secrets)): with their change's key, as part of its payload, and with a key of their own, the *record key*, which only the space's secrets key opens. A field is secret when a type of the space marks it so ([Data model](model.md#9-secret-fields)).

**Payload.** The payload of a change holds the array `[operations, sealed, restated]`:

| Item | Content |
| --- | --- |
| `operations` | The operations that everyone with the space key can read |
| `sealed` | Secret statements: an array of `[id, envelope]`, where `id` is the statement's ID and `envelope` holds the statement, encrypted with its record key with the associated data `[space, id]`; sorted by ID, without duplicates |
| `restated` | What a purge states again (section 7): an array of `[change, operations, sealed]`, sorted by the changes' IDs, without duplicates, where `change` is the ID of the change that these operations and sealed statements came from |

The IDs of the statements sealed in `sealed` and in `restated` together are those of the header's `sealed`, each once.

A sealed statement is asserted; what it supersedes is retracted in `operations`, because IDs reveal nothing, so that every replica applies the supersession, whether or not it can open the statement, and also after the statement is purged. The secret statements it supersedes are retracted with a retraction of secret statements, `[4, superseded]`, which names no entity, and so is a secret statement taken away without a new one; an ordinary statement that it supersedes, written before its field was made secret, is retracted from its entity ([Data model](model.md#5-operations)). A replica writes one in a change, for all the secret statements that the change takes away.

**Record keys** are random keys, one for each secret statement, known by the statement's ID. A record key is wrapped ([Cryptography](crypto.md#2-envelopes)) with the key derived from the space's secrets key with the context `nibkeep 2026-10 record keys`, and with the associated data `[space, id]`. A wrapped key is the CBOR array `[epoch, envelope]`, where `epoch` is the number of the secrets key. Wrapped keys are not part of changes: they are stored and travel on their own, so that they can be destroyed.

**Reading secrets.** A replica opens a sealed statement when it has the change with its payload and key, the wrapped record key and the secrets key, and asserts it with the change's timestamp. Until then it keeps the sealed statement as it is, so an archive node stores and passes on changes and wrapped keys that it cannot open. A sealed statement that does not open with its record key, or does not have its ID, is ignored. A replica may keep a few wrapped keys for one statement, such as keys wrapped with different secrets keys; it drops those that do not open with the secrets key they name. One that opens to a key whose hash differs from the one in the header of the change that holds the statement is kept, and never opens it: another change may seal the statement too, and come to hold it. If several changes seal the same statement, as devices that run one migration at once do ([Data model](model.md#12-migrations)), and otherwise only a faulty replica, the earliest counts, and of equally early ones the smallest. A replica locks its secrets by forgetting the statements it opened, and the secrets key.

**Purging.** A change whose header names a statement in its purges destroys its record key. Every replica that accepts the change deletes the wrapped key, forgets the opened statement, and ignores the wrapped key if it ever arrives again, so the value becomes unreadable everywhere, even with the secrets key. A change that purges a statement which is not sealed in a change it builds on is rejected for good. Any value can be purged ([technical design](../Technical-design.md#64-purging)), through the key of the change that holds it, which the header's purges of changes name (section 7).

## 6. Blob keys

Every blob in a space is sealed with a key of its own, its *blob key* ([Cryptography](crypto.md#6-sealed-blobs)), so that purging can destroy it ([technical design](../Technical-design.md#79-blobs)). The space's statements refer to a blob by its content hash ([Data model](model.md#2-values)). A sealed blob is stored and travels under its sealed hash.

**Wrapped blob keys.** A blob key is wrapped with the key derived from a space key with the context `nibkeep 2026-10 blob keys`, with the associated data `[space, sealed hash]`. The envelope ([Cryptography](crypto.md#2-envelopes)) holds the CBOR array `[content hash, blob key]`, so the content hash stays as secret as the content. A wrapped blob key is the CBOR array `[epoch, envelope]`, where `epoch` is the number of the space key, and it is known by the sealed hash. Like wrapped record keys, wrapped blob keys are not part of changes: they are stored and travel on their own, so that they can be destroyed.

**Secret blob keys.** The content of a secret field, such as a secret file's ([technical design](../Technical-design.md#95-secret-files)), is sealed with a blob key wrapped twice, as a secret value is (section 5). The inner envelope holds `[content hash, blob key]`, wrapped with the key derived from a secrets key with the context `nibkeep 2026-10 secret blob keys`, with the associated data `[space, sealed hash]`. The outer envelope, the wrapped blob key's, holds the CBOR array `[secrets epoch, inner envelope]` in place of `[content hash, blob key]`, where `secrets epoch` is the number of the secrets key; a hash is never an integer, so the two are told apart. A replica therefore needs a space key and the secrets key to open it, and one without the secrets learns neither the content nor its hash.

**Opening.** A replica opens a wrapped blob key with the space key it names, and drops one that does not open, or holds neither a content hash and a 32-byte key nor the number of a secrets key and an envelope. It opens the inner envelope of a secret blob key while its secrets are unlocked, and drops one that does not open with the secrets key it names, or does not hold a content hash and a 32-byte key. While it lacks the space key or the secrets key, it keeps a few wrapped blob keys for one sealed hash, and passes them on. A wrapped key it can open in part, as a secret blob key whose secrets key it lacks, is never replaced by another: only one whose space key it lacks is. A secret blob key that opens takes the place of an ordinary one opened for the same sealed hash, as only a replica that holds the secrets can make one, and any replica of the space an ordinary one. When it locks its secrets, it forgets the secret blob keys it opened.

**Sealing.** A replica seals content only with a new blob key, made for that content, and never with a blob key it received: the content hash in a wrapped blob key is only a claim, until reading the whole sealed blob checks it. Content in a secret field is sealed with a secret blob key, and other content with an ordinary one. Content that a replica already holds with a key of the same kind is not sealed again, so it is stored at most once for each. That holds across the replica's spaces too ([technical design](../Technical-design.md#79-blobs)): content that another space of the replica holds with a key of the same kind is not sealed again for a space that adds it, by an import or a move. The replica reads that sealed blob whole first, which checks the content hash its key claims, and then wraps its blob key for the space, of the same kind, with the space's own keys; a space that purged that sealed hash seals the content anew. Keys are wrapped this way only within their kind, and an AI agent's replica, which seals nothing, wraps none ([technical design](../Technical-design.md#14-ai-agents)).

**Purging.** A change whose header names sealed hashes in its purges destroys their blob keys in its space. Every replica that accepts the change deletes the space's wrapped blob keys and its sealed blobs, but those that another space of the replica keeps keys for, which stay readable through that space, and the space ignores them if they ever arrive again; another space does not. A change may name any sealed hash. To purge a blob, a replica names the sealed hashes of all the blob keys of its kind, secret or ordinary, that it has opened for the blob's content hash: the same content in a field of the other kind is sealed apart, and stays.

## 7. Purging values

Any value can be purged, through the key of the change that asserted it ([technical design](../Technical-design.md#64-purging)); a secret value is purged through its record key alone (section 5).

**Purging changes.** A change whose header names changes in its purges destroys their keys and payloads. Every replica that accepts it deletes their sealed payloads and wrapped keys, ignores them if they ever arrive again, and builds its state again without their operations. Their headers stay: their authors, times, parents and the hashes they hold. Only changes of kind `0` that the purge builds on can be purged (section 2). A statement sealed in a purged change is held by the purge that states it again, if one does.

**Restating.** The purge states again, in its payload's `restated`, everything else that the purged changes held, by the change each part came from: their operations and sealed statements, with their statement IDs, but not the assertions of the purged values. What a purged value replaced stays replaced: the purge states that as a retraction. The changes that `restated` names must be ancestors of the purge. A restated statement counts from the time of the change it came from when the space decides which value was written last, so purging never changes which value is current; it shows from the purge on, and is attributed to the purge's author. What a restated operation supersedes is superseded from the purge on. As of a time between a change and its purge, the space shows neither what was purged nor the rest of that change.

**Purging content.** A value that refers to a blob, such as a file's content, is purged with the blob: the change that purges every value holding the content hash in a field of the same kind, secret or ordinary, also names, in its purges, the sealed hashes of every blob key of that kind the replica has opened for it (section 6) ([technical design](../Technical-design.md#92-checkouts) and [secret files](../Technical-design.md#95-secret-files)). So what a purge takes away does not depend on whether the secrets are unlocked.

**Purging a value** means purging every change that asserted it: a text edited five times was asserted five times. A replica finds the changes it can see: the one that first asserted it, every other that asserted it too, as devices that run one migration at once do ([Data model](model.md#12-migrations)), or that asserted another statement under its ID, as only a faulty replica does, and the purges that state it again. A copy asserted concurrently on a replica that had not seen the purge needs a further purge. So do the values of one change that two replicas purge concurrently, one each: each purge states the other's value again.

**Restoring.** A change whose header names `restores` gives back what purges destroyed, as a copy that waits before purging does when its owner stops a purge ([technical design](../Technical-design.md#911-copies-that-wait)). It is an ordinary change that purges nothing, and names only what a purge may: changes of kind `0` that it builds on, statements sealed in changes it builds on, and any sealed hashes of blobs; one that names others is rejected for good. Of what the changes that count purge, an item stays purged unless a counting change that restores it builds on the purge: a restore does not undo a purge it has not seen. What is no longer purged is as a set-aside purge leaves it (section 8): a change waits for its sealed payload and wrapped key, and takes them from a replica that kept them, checked against the hashes in its header, and its operations count again with its own time; a statement or a blob takes its wrapped keys again. Which change holds a sealed statement is decided again. A later purge that builds on the restore purges again what it names. A change that restores holds nothing else: its header seals nothing, and its payload, once read, is empty, or it adds nothing. A purge that comes to count only after a counting change that restores builds on it, as one set aside and then accepted, destroys nothing that the restore gives back.

## 8. Which changes count

A space whose first change governs it lists its replicas, and only their changes count ([technical design](../Technical-design.md#11-revocation-and-new-keys)). Every space of NibKeep is founded so ([Identity](identity.md#2-a-new-library)); in a space where no change without parents governs, every change counts. A change that does not count is *set aside*: the replica keeps it and passes it on, as it does every accepted change, but applies none of its operations, and acts on nothing its header says: it seals and purges nothing. A change from another replica by a key that no governing change the replica can read lists, other than by the key itself or by a recovery code below, is not accepted: the replica refuses it, without rejecting it, and takes it when it comes again after such a listing. It takes a governing change that lists its own author by a recovery code, if it can read the change with the keys it holds and a governing change that it can read names the code, as below, whether either counts or not. So nobody can fill a replica with changes of keys nobody added. Whether a change counts depends on the governing changes that the replica can read, so it may change as they arrive; every replica that holds the same changes decides the same.

**Listing.** A governing change *lists* a key when it asserts the key as a replica's `org.nibkeep.signing-key`, with the key's own listing ([Identity](identity.md#8-spaces-of-ones-own)), and *revokes* a key when it asserts it, in the same text form, as a replica's `org.nibkeep.revoked`: a revocation names the key it revokes. A governing change lists a key on a record only if it also asserts, on that record, a listing of the key whose space is the change's space, whose record is that record and is derived from the space and the key, whose owner the change asserts as the record's `org.nibkeep.owner`, and no other, whose encryption key's hash is that of the record's `org.nibkeep.encryption-key` that the change asserts, and of no other it asserts there, whose mark is `true` exactly when the change asserts `org.nibkeep.ai-agent` on the record, and whose signature verifies. Any other statement of a key lists nothing, for any rule of this section: not for when a key was listed, nor for whether it is an AI agent's, nor for which keys a replica takes changes of. The space's first change counts if it lists its own author. Another governing change counts only if a counting governing change before it, by timestamp and then by ID, lists its author's key, or it lists its author by a recovery code; an ordinary change, only if a counting governing change lists its author's key.

**Listing by a recovery code.** A governing change lists its own author *by a recovery code* ([Identity](identity.md#11-recovery-codes)) if it asserts, on a record it lists the author's key on, a recovery listing whose space is the change's space, whose record is that record, whose key is the author's, whose owner the change asserts as the record's `org.nibkeep.owner`, and no other, whose encryption key's hash is that of the record's `org.nibkeep.encryption-key` that the change asserts, and of no other it asserts there, and whose signature verifies; and asserts no `org.nibkeep.ai-agent` there. Such a listing lists its author only if a counting governing change that it builds on names the listing's recovery key for its owner, with a statement of `org.nibkeep.recovery-key` on the record derived from the space, the owner and the recovery key, whose signature verifies; and if every counting governing change that revokes that code on that record, with a statement of `org.nibkeep.recovery-revoked` naming the recovery key, builds on it, as a revoked replica's changes count. Its author's key is known, for which changes the replica takes, once a governing change it can read names the code, as above, whether either counts or not. The change must also list the key on that record with the key's own listing, for the same owner, as every listing does (above). In a space with members, the code's statement counts only from a replica of the owner's, so a code that another member named lists nobody.

**Spaces with members.** A space whose first change asserts a statement of `org.nibkeep.role` has members, as every space but a user's personal one does ([Identity](identity.md#8-spaces-of-ones-own)).

**Roles.** In a space with members, a change also counts only if its author's role at the change allows it ([technical design](../Technical-design.md#13-sharing)):

- *Whose key it is.* A key's member at a change is the owner that the latest counting listing of the key, among the governing changes that the change builds on, names. A change whose author no such listing names has no member, and counts for nothing: a replica writes in such a space once it holds its own listing. The space's first change lists its own author, and a change that lists its author by a recovery code, as above, is the listing's owner's, with that member's role at the change, an admin's too.
- *A member's records* at a change are the member's own record, and those of the replicas that counting listings among the governing changes it builds on list for the member, with their devices' records, derived from the space and the key ([Identity](identity.md#8-spaces-of-ones-own)). *Members' records* at a change are those that the governing changes it builds on, counting or not, name by user IDs, roles and listings, so that whose an entity is never depends on a change that the change does not build on.
- *The role at a change.* Of the roles that counting governing changes it builds on give the member, as statements of `org.nibkeep.role` on the member's record (`admin`, `editor`, `viewer`, or `none` for one who left or was removed), the lowest of those that no other of them builds on; lowered by each counting governing change that gives the member a lower role and that neither builds on the change nor is built on by it. So nobody acts on a role they did not know they had, and what someone did without knowing that they had lost one is set aside, as a revoked replica's changes are.
- *Ordinary changes.* A viewer's role allows operations on the member's own records. An editor's also allows operations on every other entity but other members' records; purges of changes whose authors' members at them were the member, and of statements sealed in such changes; and sealed statements, whose entities only those who open them see, and retractions of secret statements, which take away nothing else, whatever their IDs are ([Data model](model.md#5-operations)). An admin's allows anything, purges of other changes, of statements sealed in them and of blobs included. What a change restores needs what a purge of it would. Each operation is judged by the entity it names ([Data model](model.md#5-operations)); one that names none, of an unknown kind, or of the earlier form that supersedes something, needs an admin.
- *Governing changes.* Every member may list and revoke the replicas of their own member, and state what is on those replicas' records, give space keys and secrets keys, and take their own role away, with `none`. A member may name a recovery code of their own, and revoke it, on the record derived from the space, their member's record and the code's recovery key ([Identity](identity.md#11-recovery-codes)), where their member's record is one of theirs in the space itself or, for a path through a group, their record in the group that lists their key: a statement of `org.nibkeep.recovery-key`, `org.nibkeep.recovery-entry` or `org.nibkeep.recovery-revoked` on any other record counts for nobody, an admin included, and one whose text names no key needs an admin, as a later version may give it a meaning. What an assertion replaces needs what a retraction from its entity would. Everything else needs an admin: roles, a role this version does not know included, members' user IDs, acceptances, fields made secret for good, a user's spaces, that a replica takes the secrets from itself, as `org.nibkeep.secrets-from` naming its own record, which sets them up ([Identity](identity.md#6-secrets)), operations of unknown kinds, and statements of fields this version does not know (section 1), and listing the replica that joins on the record of a member that the same change makes, which no governing change it builds on names by a user ID or a role, as an invitation does. Listing or revoking another member's replicas counts for nobody, an admin included. Whether the space allows AI agents, `org.nibkeep.ai-agents`, `true` or `false`, needs an admin, and a listing that marks its replica as an AI agent's counts only where the space allows AI agents at the change: where, of the counting governing changes it builds on that state it, and the change itself, those that no other of them builds on all say `true`; a space allows none until an admin says it does, and a value this version does not know allows none. The statement counts on whatever entity it is, by convention the space's own, and a retraction of it takes nothing back: an admin states `false`. The space's first change counts by its listing alone.
- *Never without an admin.* Of two governing changes that lower each other's authors' roles below what they need, neither building on the other, the one whose author became an admin later sets nothing aside. When someone became an admin is the earliest governing change, by timestamp and then by ID, that gives their record `admin` and whose author's member had become one before it, back to the first change, whether those changes count or not; a key's member for this is the owner that its first listing names, or that a later listing names whose author had become an admin before it, as when a member comes back; a record made for a member through a group (section 9) is the first listing of the key it names, made by its author. One whose time is unknown became an admin after everyone else. Then, of the counting governing changes, one that leaves the space with members and no admin, by the counting ones it builds on and its own statements, does not count; and if those that count leave none only together, the latest that took the role from an admin does not count. Each time one is set aside, the others are decided again.
- *Acceptance.* There, an acceptance counts only from an admin, as above, and an accepted change counts only if the role that its author's member had by the governing changes it builds on allows it: acceptance lifts only what a lower role, a removal or a revocation that it did not know of set aside.

**Revocation.** A change whose author's key is revoked counts only if it is an ancestor of every counting change that revokes that key, or is that change itself: only what every replica that revoked it had. Of two governing changes that each revoke the other's author, and of which neither is the other's ancestor, the one by the key listed through a recovery code, or else by the key listed later, does not set the other aside: of two replicas that revoke each other, one listed through a code loses to one that was not, and of two of one kind, the one added first stays. When a key was listed is the earliest governing change, by timestamp and then by ID, that lists it and whose author was listed before it, back to the space's first change, which lists its own author; a change that lists its own author does not count for this either, but one that lists it by a code, if a governing change before it, whose author was listed before that change, names the code for the listing's owner, gives it the time of that change. A key is listed through a code if the change that gave it its time lists it by a code, or is by a key listed through a code. So a key that nobody listed, or listed itself, cannot make another key older by a listing it dates early, and a code beats no device in hand. Changes that these rules leave undecided, which only rings of three or more such revocations do, do not count.

**AI agents.** A key is an AI agent's if the governing change by which it was listed, in the sense of the rule for revocations above, asserts `org.nibkeep.ai-agent`, with the value `true`, on the record that it lists the key for, whether that change counts or not, so that what decides it depends on no change that it decides. A governing change by an AI agent's key does not count, nor lists anything. An ordinary change by an AI agent's key does not count if its header purges, restores or seals anything, or if its payload asserts a statement that an AI agent may not write ([Identity](identity.md#5-ai-agents)), or retracts secret statements, which an AI agent cannot read: the header decides as soon as the change is accepted, and the payload once it is read, from what the payload holds alone. Such a change is never accepted. In a space with members, an ordinary change by an AI agent's key also counts only where the space allows AI agents at the change, by the counting governing changes it builds on, as for listings above, and not if a counting governing change that says the space allows none neither builds on it nor is built on by it: so stopping AI agents ends them as a removal does, and what they wrote without knowing of it is set aside, which an admin may accept. Allowing them again lets what an AI agent writes after count again.

**Choices.** In a space with members, a governing change states a device's *choice* of the space as `org.nibkeep.space-choice` on the record derived from the space and the device's key ([Identity](identity.md#8-spaces-of-ones-own)), with the device's signature: a choice that does not verify, names another record or another space, lists nothing and counts for nothing. Only a replica of the device's member states it there, the device itself or another, an admin of another member's not even. Of a key's choices that counting governing changes state, the one with the highest number *stands*, of two with one number the one that does not hold the space; a key with none holds the space. A key whose standing choice does not hold the space is ended there, as a removal ends a member's replica: a governing change by the key does not count if the standing choice among the governing changes it builds on does not hold the space, and an ordinary change by the key counts only if that choice holds it, and not if a counting choice not to hold it that outranks that one neither builds on it nor is built on by it, which an admin may accept. A key comes back only by a counting choice of its own to hold the space, with a higher number, which another replica of its member states, as its own governing changes count for nothing while it is ended: a listing of it again changes nothing. A change by a key whose standing choice, among the governing changes it builds on and the change itself, does not hold the space gives nothing out: a key whose rotation it is, or that it gives, is not given out ([Identity](identity.md#4-revoking-replicas)). In a space without members, the personal space too, choices count for nothing.

**Secret fields.** An ordinary change does not count if its payload asserts, without sealing it, a statement of a field that a counting governing change makes secret for good, as a statement of `org.nibkeep.secret-field` ([Data model](model.md#9-secret-fields)), unless such a change for that field builds on it: only values written before the field became secret count in plain. Nor does it count if it states again such a statement of a change that no such change builds on. Every replica holds key 0, which wraps every governing change, so it reads that the field is secret, and every replica seals what it knows to be secret. A value written in plain since comes from a replica that turned against its user, which could otherwise replace a password with one of its own, even in a change whose parents leave the mark out, as superseding needs no ancestry; or from a device that wrote at the same time and did not know yet, whose value is set aside too. Fields whose names start with `org.nibkeep.` are left out, as no replica seals them. The payload decides once it is read; a governing change that makes a field secret has the ordinary changes that it does not build on decided again.

**Acceptance.** An ordinary change counts, whatever the rules above say but those of roles, if a counting governing change by another key, which builds on it, names it in a statement of `org.nibkeep.accepted`, whose value is the change's ID as text ([Encoding](encoding.md)): a replica accepts only what it had, so that a replica cannot accept, before it is revoked, what it keeps back to send later. A governing change is never accepted: a replica that a revoked one revoked stays, whatever is accepted.

**Setting aside.** Which accepted change holds a sealed statement is recorded whether it counts or not, one that counts first, so that a purge of the statement is decided alike everywhere. A change that restores, set aside, restores nothing: what it restored is purged again, and destroyed again where it came back. A change that counted and is set aside is taken out of the state, which is built again without it. A replica deletes from its storage only what purges that count destroyed: a set-aside purge deletes nothing, and one that comes to count deletes then. A purge of a set-aside change leaves it set aside. What its header purged is no longer purged, unless a counting change purges it too: a change whose key and payload it destroyed is pending again, and takes them from another replica that has them; a statement or a blob whose key it destroyed takes its wrapped key from another replica. Which change holds a sealed statement is decided again among those that count. A set-aside change that comes to count is taken in as if it had just been accepted.

**Every replica reads every governing change.** A governing change is wrapped with the space key of number 0, which every replica holds, and one of another epoch is refused (section 2): else a replica that turned against its user could give a new key to some replicas and not to others, and wrap with it a revocation that only some of them read, which would decide otherwise on each, for good, as no replica gives a revoked one a key. A replica builds a governing change that revokes a replica or sets a role on no governing change whose payload it has not read, and on no change that builds on one: such a change may revoke it, or take its role away, sent without its payload by the replica it revoked, and the replica's own revocation of that one would then build on it, and be set aside, though it would stay by revoking that one back. Its other changes build on every change it holds.

A governing change whose payload the replica cannot read yet lists and revokes nothing, and counts once it is read, if the rules say so; one whose payload does not have the form a governing change must (section 1) lists and revokes nothing at all. What says who the replicas are is what the governing changes that count assert: their retractions change nothing of it, as revoking is the only way out ([Identity](identity.md#4-revoking-replicas)). Governing changes are few, so a replica reads all of them to decide; a revocation also reads the revoked keys' changes, and walks the history from the revocation down to the oldest of them.

## 9. Groups

A group is a space with members and no data of its own, with the roles and rules of section 8 ([Technical design](../Technical-design.md#138-groups)). A space that a group is in follows the group's governing changes, which the replica keeps in a log of the group's own, and decides them by the group's own rules. They take effect in the space at the space's own governing changes that name them, its *anchors*. A replica follows, for good, each group whose record a governing change of the space, or of a group it follows, makes, as an anchor of a group it no longer followed could not count. It takes the changes of the keys that the governing changes of a group it follows, and that a record in the space or in a group it follows names, list, counting or not, but AI agents' keys, as it does those of the keys that the space lists (section 8).

**Statements.** In the space, `org.nibkeep.group` on a member's record says which group the record is: the canonical encoding of `[group, root, key]` in base64url without padding, where `root` is the ID of the group's first change and `key` the hash of its first key, computed as the hash of a change key is ([section 1](#1-changes)), which the log leaves to the replicas. That statement is the group's *addition*. A record is a group's at a change if a governing change that the change builds on, or the change itself, states one on it, whether that change counts or not; making one needs an admin, as making a member's record does. A role on a group's record is the group's role in the space, and `admin` there counts for nothing, as a group is never an admin. `org.nibkeep.anchor` is an anchor: `[group, changes]`, the group's governing changes that it names, by convention those that no other of them builds on. Every member may state one, on any entity, by convention the group's record; an anchor that names a change that the replica holds as no governing change of a group it follows cannot count yet. In the group, `org.nibkeep.joined` is the group's agreement to join a space, `[space, root, addition]`: the space, its first change, and the statement ID of the addition there. `org.nibkeep.withdrawn`, in the same form, withdraws it for good. Both need an admin of the group, as statements that section 8 gives no other role. Every member may state `org.nibkeep.group-key` in a space and `org.nibkeep.join-request` in a group, which [Identity](identity.md#10-groups) describes, as they give keys and ask; `org.nibkeep.space-kind` needs an admin, and a replica reads it in a space's first change alone.

**What a change knows.** A change of the space *knows* the group changes that the counting anchors among the governing changes it builds on name, and every one they build on; an anchor, for whether it counts itself, knows those that it names too. The group changes that the space's counting anchors name, with those they build on, are decided by the group's rules among themselves alone, as section 8 decides a space's. So a group change that no counting anchor names changes nothing in the space yet; one that the group's rules set aside, once the space knows why, gave nothing at any change that relied on it; and a removal that they set aside took nothing.

**A group in the space.** At a change, a group is in the space if a change that it builds on, or the change itself, makes the group's record, the first such change naming its addition, if the record names the first change of the group's log that the replica follows, so that no other log is taken for the group, and a counting agreement that the change knows names that addition and the space's first change, and no counting withdrawal that it knows withdraws it. The group's role there is its record's, by the rules of section 8.

**Keys listed through a group.** At a change, a key is listed through a group in the space if a counting listing among the group changes it knows lists it, the latest naming its member there, but an AI agent's key, which counts only where the space lists it itself, and one that a counting revocation among them revokes. Such a key counts as listed for the rules of section 8, and so does, for a change that it signed, a key that a counting listing among the group changes that the counting anchors name lists, in any group the space follows, as its standing at the change decides whether the change counts, also once its paths have ended. The path through the group gives the lower of the group's role in the space and the member's role in the group by the group changes that the change knows, and never more than an editor's. A key that a counting revocation of a group, which the change knows, revokes is ended in the space on every path, the space's own record included.

**Groups inside groups.** A group in the space, or inside one, at every level, may have groups in it, as a space does; the space knows each group at every level through its own anchors alone. At a change, a group is inside a group that is in the space, or inside one that is, if a change of the outer group that the change knows makes the inner group's record, the first such change naming its addition, if the record names the first change of the inner group's log that the replica follows, if the outer group's counting changes that the change knows give the record a role other than `none`, and if a counting agreement of the inner group that the change knows names that addition and the outer group's first change, and no counting withdrawal that it knows withdraws it. Every group's changes are decided by its rules among those that the counting anchors name, as for a group in the space, the groups inside it left out. A key listed in the inner group gets a path as one listed through the outer group, with the member's role in the inner group lowered, at every level, to the role of the inner group's record. A path passes each group once, and never the space, so groups that hold each other give nothing through the cycle. Every path counts, however many there are.

**Direct members and keeping out.** In the space, `org.nibkeep.made-for` on a member's record names a key of a member through a group: a replica's listing of its own key on that record, with the listing it signed, counts if a counting change that it builds on, which needs an admin, states it on the record naming a key of the replica's person, as below; so the person becomes a direct member, with the record's role. `org.nibkeep.kept-out` on the record derived from the space and a key says whether the key's person is kept out of the space through groups: `true` on a record of the author's person's keys needs any member, as one leaves the space and stays in the group, and anything else an admin. At a change, a person is kept out if, for the record of one of their keys, of the counting changes that it builds on and that say so, one that no other of them builds on states `true`; they then have no path through a group. A counting change that keeps the author's person out and that the change neither builds on nor is built on by lowers every such path, as a lower role does. Keeping out a person whom nothing else gives a role ends their replicas, as a removal does, and a removal from the space ends no replica of a person whom a group still gives a role.

**One person.** A key's records at a change are joined into one person where a key is listed on two of them and is not revoked, by the counting governing changes of the space that the change builds on or by a counting revocation of a group that it knows: the space's own records, by its counting listings among the changes the change builds on, and the members' records in the groups in it, by the listings above. Records are never joined by the user IDs they name. A person's member is the space's own record whose listing names the key, if one does, or else the smallest of their records in the space, or else of their records in groups. Their role at the change is the highest over every path: each of their records in the space, by the rules of section 8, and each path through a group. Their records, for what a role allows, are those of each of their records in the space, and the records in the space of each of their keys' replicas and devices, derived from the space and the key (section 8). Every member may revoke their keys in the space, whichever path lists them.

**What counts.** The rules of section 8 apply, with the person's role over every path. A path is lowered at a change by the counting governing changes of the space that give the path's record in the space a lower role and that neither build on the change nor are built on by it, as section 8 says; through a group, also by each group change that the change does not know, that the counting anchors name, and that gives the path's member a lower role in the group, or withdraws the group's agreement, unless one of its *first anchors*, the counting anchors that name it and build on no other counting anchor that names it, builds on the change; through a group inside a group, also by each change of the outer group that gives the inner group's record a lower role, and each change of the inner group that withdraws its agreement to join the outer group, at every level, with the same exception. A group change that revokes the change's key lowers every path, unless one of its first anchors builds on the change. A change is set aside if every path that allowed it is lowered. So a late anchor, or an anchor of a later group change, takes away nothing that a first anchor kept, and a removed member's own anchor keeps nothing, as it knows the removal and counts for nothing.

**Which anchors count.** Which anchors count decides what the groups give, which decides which anchors count. A replica takes every anchor that can count to count, decides, and decides again with those that counted, until they are those taken. After eight rounds, it takes only those that counted and were taken, which are fewer each time, and sets aside the anchors it does not take, until those that count are those taken. Every replica that holds the same changes decides the same.

## 10. Claims to the admin role

In a space with members, a direct member claims the admin role with `org.nibkeep.claim`, `true`, on their own record, which needs an editor ([Technical design](../Technical-design.md#139-claims-to-the-admin-role)); `org.nibkeep.rejected`, naming a claim's change by its ID, rejects it, which needs an admin; and `org.nibkeep.seen`, naming a claim's or a rejection's change, shows that a replica saw it, on the replica's own record, which needs any member.

**Seen.** A change *sees* a claim, or a rejection, if it is a governing change that builds on it and its author is a person, as section 9 joins records into one, none of whose records is the claimant's, or the rejector's, whether it counts or not. A claim is first seen at the earliest change, by timestamp and then by ID, that sees it.

**Taking effect.** At a change of the claimant, a counting claim that the change builds on makes their record an admin's if the record's role there is an editor's, and the change is timestamped at least 30 days after the earliest change that sees the claim and that the change builds on or is; until 60 days after it, the role allows no acceptance, rejection of a claim, `admin` given to anyone, lower role given to an admin by the change's ancestors, or, in an ordinary change, purge or restore. So a claimant lowered below an editor, or removed, gets nothing from the claim, and one lowered so without the change's knowing loses it there too. The claim gives nothing at any change if a counting change retracts its statement, which withdraws it, or if a counting rejection of it is seen at or before 60 days after the claim was first seen, however the rejection is dated. For seniority (section 8), the claimant became an admin 60 days after the claim, the earliest it can be settled, so they are junior to every admin before, and those they make get times after theirs.

## 11. Accounts of copies

Each replica tells the other replicas of a space what it holds there, in an *account* that it signs and seals with the space key, and that they pass on ([Technical design](../Technical-design.md#96-where-the-copies-are)). An account is split into *pages*, so that what changes is issued again alone. A page is the CBOR array `[1, header, body, signature]`:

| Item | Content |
| --- | --- |
| `header` | `[space, epoch, author, page, issued]`: the space's ID; the number of the space key that seals the body (section 1); the verifying key of the replica that issued the page; which page it is, below; and when it was issued, in milliseconds since 1970 (UTC) |
| `body` | An envelope ([Cryptography](crypto.md#2-envelopes)) of what the page tells, sealed with the key derived from that space key with the context `nibkeep 2026-11 accounts`, with the canonical encoding of the header as associated data |
| `signature` | The author's signature ([Cryptography](crypto.md#4-signatures)), with the context `nibkeep account`, of the canonical encoding of `[header, body]` |

A page's number says what it tells:

| Page | Number | Body |
| --- | --- | --- |
| The head | 0 | `[disk, role, away, heads, damaged, unrepaired, waits]`: the ID of the replica's disk in the space, as a hash; its device's role as its user marked it, `archive` or `everyday` ([Identity](identity.md#1-users-people-devices-and-replicas)); whether its device is kept away from home; the replica's heads, sorted, so that the space's changes it holds are these and what they build on; how many of its copies of the space's files its checks found damaged in the 4 weeks before the page was issued, those still damaged included; and how many of those are damaged still ([Technical design](../Technical-design.md#97-checking-and-repair)); and how many days its device waits before it destroys what a purge destroys, as the wait in force when the page was issued, 0 for none ([Technical design](../Technical-design.md#911-copies-that-wait)) |
| Sealed blobs | 256 + `n` | `[[sealed hash, checked], …]`: the sealed blobs of the space that the replica holds whose sealed hash's digest starts with the byte `n`, sorted by sealed hash, each with when the replica last read it in full and found it intact, in milliseconds since 1970, or 0 if it never did |
| Plain copies | 512 + `n` | `[[file, content, checked], …]`: the files of the space whose ID starts with the byte `n` of which the replica's device holds an unchanged plain copy, an original kept where it was found or a checkout, that its last check did not find damaged, each with the content hash of what the copy holds, and when the replica last read such a copy in full and found that content, in milliseconds since 1970, or 0 if it never did; sorted by file and content |

A page longer than 4 MiB, or that lists something twice, out of order, or on another page than its first byte names, does not read.

**The disk's ID** is the BLAKE3 hash of the 32 bytes of `BLAKE3-keyed-hash(key, name)`, with the key `BLAKE3-derive-key("nibkeep 2026-11 disk", space ID)` and the space ID as its 16 bytes, where `name` is `disk`, a zero byte and what names the disk ([Storage](storage.md#11-which-replica-is-here)), or, where nothing names it, `replica`, a zero byte and the replica's verifying key.

**Issuing.** A replica issues a page again only when what it tells changes, and a page it no longer has anything for as an empty one; each later than its last page of that number, at least by a millisecond. It keeps only its own latest pages.

**Taking.** A replica keeps a page that another replica sent if it reads, its signature checks, its disk keeps 1 GiB free after it, as for blobs ([Sync](sync.md#3-syncing)), it is of the space, its author is a replica of the space that counts there, listed and neither revoked nor removed, and not itself, and it is later than the page of that author and number that it keeps, if any: issued later, or at the same time with a larger hash of its encoding. Only the pages of replicas that count are counted, or passed on. A page's body needs the space key to open, but its signature does not: a replica keeps and passes on a page it cannot open yet.

**Pages about backups.** A replica that updates a backup ([Storage](storage.md#6-backups)) issues the backup's account in each space that the backup holds and where the replica counts, as pages that it signs: their header's `page` is `[backup, number]`, with the ID of the backup's record as an identifier ([Encoding](encoding.md#2-identifiers)) and the page's number, 0 for the head or `256 + n` for sealed blobs; a backup's account lists no plain copies. A backup's head is `[disk, away, heads, damaged, unrepaired, update, waits]`: the backup's disk's ID, as above, where what names the disk is what names the drive that holds the backup's folder ([Storage](storage.md#11-which-replica-is-here)), or, on a network share or where nothing names it, `backup`, a zero byte and the backup's ID as its 16 bytes; whether the backup is marked as kept away from home; the issuing replica's heads, which the backup holds after the update; how many of its copies of the space's blobs checks found damaged in the 4 weeks before, and how many of those it holds no intact copy of, so that no space learns of another's; the number of the update ([Storage](storage.md#6-backups)); and how many days the backup waits before what a purge destroyed leaves it, as its record says after the update, 0 for none. Its pages of sealed blobs list the blobs that the backup holds and whose key a pack of the space holds, each with when it was last read in full. Such pages are issued, kept and passed on as a replica's own are, by author, backup and number, but a replica keeps pages of each author about at most 8 backups in a space, so that none fills the others' disks with pages about backups it made up. Of the pages about one backup that a replica keeps, of replicas that count in the space, this one included, those of the author whose head names the greatest update, or, of equal updates, was issued latest, tell of the backup.
